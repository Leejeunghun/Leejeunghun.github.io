어제 코드를 읽으면서 sc6-bsp가 EVerest의 heartbeat를 받기만 하고 **아무것도 하지 않는다**는 것을 다시 봤다([코드 읽기 1]({% post_url 2026-11-09-sc6-code-reading-everest-sc6-bsp %})). 하드웨어 기능이 아니라서 무시해도 된다고 생각했던 부분이다. 그런데 거꾸로 생각하면 이렇다. EVerest가 충전 중에 멈추면 K1(주 릴레이)을 끄라고 말해 줄 주체가 사라진다. **K1은 붙은 채로 남는다.**

오늘 한 일과 결과를 먼저 정리한다.

| 일 | 결과 |
|---|---|
| sc6-bsp heartbeat 감시 | ✅ 3초 끊기면 K1 OFF + CP F, 다시 오면 같은 거래로 충전 재개 |
| 덤: 회복 뒤 상태 불일치 | ❌ → 끊기기 전 출력을 복원하도록 고침 (r0.5) |
| OCPP 재접속 간격 | ✅ 최대 약 3분 → **약 47초** (실측 7 → 15 → 34초) |
| 오프라인 충전 | 지금처럼 **충전 안 함** 유지 (기획 답 대기) |
| 중간 이미지 + 새 SD 회귀 | ✅ 이미지에 든 sc6-bsp로 NTP, 충전, heartbeat 모두 통과 |

## 1. heartbeat는 서버 연결이 아니다

먼저 헷갈리기 쉬운 점이 있다. 이 일을 시작할 때 "서버와 끊겨도 오프라인으로 동작해야 하니 빼는 게 맞지 않나"라는 이야기가 나왔다. 하지만 두 연결은 서로 다르다.

```text
[보드 안]  EVerest ──e2m/heartbeat (1초마다, MQTT)──► sc6-bsp     ← 오늘 감시하는 것
[보드 밖]  EVerest ══wss══ OCPP 서버(SteVe)                        ← 오프라인 충전과 관련된 것
```

heartbeat는 **같은 보드 안**에서 EVerest의 BSP 모듈(`evse_board_support_API`)이 sc6-bsp에게 보내는 "나 살아 있다"는 신호다. 간격은 EVerest 구성의 `cfg_heartbeat_interval_ms: 1000`이다. 서버가 끊겨도 계속 온다. 이 신호가 끊긴다는 것은 **보드 안의 충전 제어 프로그램이 멈췄다**는 뜻이다. 그때는 끄는 것이 맞다.

## 2. 감시 넣기

### 2-1. 언제 끊겼다고 보나

| 항목 | 값 | 이유 |
|---|---|---|
| 시간 | `HEARTBEAT_TIMEOUT_MS=3000` | heartbeat 간격(1초)의 3배. `0`이면 감시 안 함 |
| 시작 | **첫 heartbeat를 받은 뒤부터** | EVerest가 뜨는 데 수십 초 걸린다. 그동안은 원래 안전 상태다 |
| 조건 | MQTT가 연결돼 있을 때만 | MQTT 브로커가 끊긴 경우는 원래 있던 처리(안전 상태)가 맡는다 |

설정은 `/etc/default/sc6-bsp`에 한 줄로 넣었다.

```sh
# EVerest heartbeat(보드 안 MQTT, 서버 연결과 무관) 가 이 시간 동안 없으면 K1 OFF + CP F.
#   EVerest 구성 bsp_1 의 cfg_heartbeat_interval_ms(1000) 의 3배. 0 = 감시 안 함
HEARTBEAT_TIMEOUT_MS=3000
```

### 2-2. 끊기면

메인 루프에서 CP를 한 번 읽을 때마다 확인한다. 끊겼으면 지금 출력을 저장해 두고 안전 상태로 간다.

```c
if (C.heartbeat_timeout_ms > 0 && connected && hb_seen && !hb_lost &&
    now_ms() - hb_last_ms >= C.heartbeat_timeout_ms) {
	hb_lost = true;
	saved_mode = mode; saved_duty = duty; saved_allow = allow_power_on;   /* 2-4 에서 씀 */
	logm("EVerest heartbeat %ld ms 없음", now_ms() - hb_last_ms);
	safe_state("EVerest heartbeat 끊김");   /* K1 OFF, CP F */
	same = 0;                               /* CP 판정을 처음부터 다시 */
}
```

K1을 켜는 함수 `relay_apply()`의 조건에도 `!hb_lost`를 더했다. 끊긴 동안에는 어떤 경로로도 K1이 붙지 않는다.

```c
bool want = connected && !hb_lost && enabled && allow_power_on && cd && !any_fault();
```

### 2-3. 시험 방법: 죽이지 말고 얼린다

EVerest를 `kill`로 죽이면 manager가 다른 모듈까지 정리해 버린다. 실제로 걱정하는 상황은 **멈춤(hang)** 이다. 그래서 BSP 모듈 프로세스만 `SIGSTOP`으로 얼렸다가 `SIGCONT`로 풀었다.

```sh
kill -STOP $(pgrep -f evse_board_support_API); sleep 6; kill -CONT ...
```

첫 시도는 무효였다. 원격 SSH 창이 하나뿐이었는데, EVerest를 띄운 창이 화면을 차지해서 얼리는 명령을 칠 수 없었다. 그래서 **창 하나에서 처음부터 끝까지 도는 스크립트**(`test-heartbeat.sh`)로 바꿨다. 이 스크립트는 다음을 한 번에 한다.

1. EVerest를 백그라운드로 띄운다.
2. 지그가 C가 되어 K1이 켜지기를 기다린다.
3. N초 동안 얼렸다가 푼다.
4. 로그를 모아 출력한다.

(두 번째 시도에서는 CP가 2분 내내 12.00 V였다. 지그를 잘못 꽂은 것이었다. 40개 샘플이 모두 정확히 12 V면 CP 선에 저항이 하나도 안 걸려 있다는 뜻이다.)

### 2-4. 1차 시험: 끄기는 했는데 다시 켜지지 않았다

첫 번째 판(r0.4)은 heartbeat가 다시 오면 CP를 X1(+12 V 고정)로 되돌리기만 했다.

```text
11:39:15.557 K1 ON (allow_power_on)                      ← 충전 중 (거래 16)
11:39:19.331 얼림
11:39:21.438 EVerest heartbeat 3007 ms 없음
11:39:21.439 안전 상태: K1 OFF, CP F (EVerest heartbeat 끊김)
11:39:25.352 EVerest heartbeat 회복
11:39:25.353 CP X1 (+12V, heartbeat 회복)
11:39:26 ~ 34  상태 C, K1 OFF, 듀티 100%                   ← 계속 이 상태
```

끄기는 설계대로였다. 문제는 그다음이다. **서버에는 계속 `Charging`이 떠 있는데 실제로는 K1이 꺼져 있었다.**

원인은 EVerest가 명령을 보내는 방식에 있었다. EVerest는 PWM 듀티와 `allow_power_on`을 **바뀔 때만** 보낸다. EVerest는 BSP가 끊김을 겪은 줄 모른다. 그래서 "PWM 53.3%가 켜져 있고 K1도 허락해 뒀다"고 믿고, 같은 명령을 다시 보내지 않는다. BSP가 X1로 되돌려 버리면 둘의 생각이 영영 어긋난다.

안전 문제는 아니다. K1은 꺼져 있었다. 하지만 충전이 재개되지 않고, 서버는 틀린 상태를 보고 있다.

### 2-5. 고친 판(r0.5): 끊기기 전 출력으로 복원

회복할 때 BSP 마음대로 출력을 정하지 않는다. **EVerest가 마지막으로 시킨 출력**으로 되돌린다.

```c
static void hb_recover(const char *why)
{
	hb_lost = false;
	logm("EVerest heartbeat 회복 (%s)", why);
	if (enabled) {
		cp_output(saved_mode, saved_duty);     /* PWM 53.3% 등 */
		allow_power_on = saved_allow;
		logm("끊기기 전 출력으로 복원: ...");
	}
	pub_capabilities();                        /* EVerest 에 현재 상태 다시 알림 */
	if (cp_state) pub_event((char[]){ cp_state, 0 });
	pub_active_errors();
	relay_apply("heartbeat 회복");             /* 여기서는 아직 안 켜짐 (same = 0) */
}
```

지킨 규칙은 세 가지다.

1. **K1은 바로 켜지 않는다.** 끊길 때 CP 판정 횟수를 0으로 돌려 두었다. 그래서 새로 읽은 CP가 C로 디바운스 횟수만큼 연속 확인돼야 `relay_apply()`가 K1을 켠다. 다섯 조건도 모두 다시 따진다.
2. **heartbeat가 아닌 메시지도 "살아 있음"으로 본다.** EVerest에서 어떤 메시지든 오면 먼저 회복 처리를 한다.
3. **가장 새 명령이 이긴다.** 회복 처리를 먼저 하고 그 메시지를 처리한다. 끊긴 동안 쌓였던 EVerest 명령이 있으면 복원값을 덮어쓴다.

```c
/* on_message(): 락을 잡은 뒤 가장 먼저 */
hb_last_ms = now_ms();
if (hb_lost)
	hb_recover(op);
/* ... 그다음 원래 메시지 처리 */
```

### 2-6. 결과: 두 갈래 길

얼리는 시간에 따라 두 가지 경로가 나왔다.

| 시험 | 얼림 | K1 꺼진 시간 | 서버 | 경로 |
|---|---|---|---|---|
| r0.4 | 6초 | 계속 | Charging (틀림) | ❌ |
| r0.5 | 6초 | 약 6.6초 | Faulted → **SuspendedEVSE** → Charging | EVerest 고장 처리 |
| r0.5 | 4초 | **약 2초** | **Charging 그대로** | BSP 복원만으로 |
| r0.5, 새 SD | 4초 | 약 4.8초 | Faulted → SuspendedEVSE → Charging | EVerest 고장 처리 |

4초 시험(거래 18)이 의도한 장면이다.

```text
11:47:44.471 K1 ON (allow_power_on)
11:47:48.367 얼림 (4초)
11:47:50.415 EVerest heartbeat 3005 ms 없음
11:47:50.415 안전 상태: K1 OFF, CP F (EVerest heartbeat 끊김)
11:47:52.382 EVerest heartbeat 회복 (heartbeat)
11:47:52.382 끊기기 전 출력으로 복원: CP PWM 53.3%, allow_power_on = true
11:47:52.430 K1 ON (CP C/D 안정)                ← 복원 48 ms 뒤, CP C 를 다시 확인하고
```

EVerest는 아무 일도 없었던 것처럼 계속 `Charging`이었다.

6초를 얼리면 EVerest 쪽 감시도 걸린다. BSP 모듈은 sc6-bsp에게서 약 5초 동안 신호를 못 받으면 `CommunicationFault`를 낸다. 풀리는 순간 이 오류가 났다가 바로 풀렸다. EVerest는 그 과정에서 충전을 잠시 멈췄다(`SuspendedEVSE`). 그리고 X1과 PowerOff를 보낸 다음, 3초 뒤 PWM과 `allow_power_on`을 **새로 보냈다**. BSP가 복원해 둔 값을 EVerest의 새 명령이 덮어쓴 것이다. "가장 새 명령이 이긴다"는 규칙이 실제로 확인됐다.

새 SD에서 한 4초 시험은 6초와 같은 길로 갔다. 멈춘 시간은 4초지만, 멈추기 직전 BSP 모듈이 받은 마지막 메시지가 1초쯤 전이었다면 합쳐서 5초를 넘는다. **4초는 두 길이 갈리는 경계값**이다. 어느 쪽이든 결과는 같다. K1을 먼저 끄고, 같은 거래로 충전을 이어 간다.

## 3. 재접속 간격: 최대 3분 → 47초

[11/06 끊김 시험]({% post_url 2026-11-06-sc6-m8-5-network-loss-libocpp-patch %})에서 본 재접속 대기는 9 → 21 → 48 → 97초였다. 네트워크가 돌아와도 충전기가 서버에 최대 3분 가까이 늦게 보일 수 있다. 이 간격을 정하는 식은 libocpp에 있다.

```text
1번째 대기 = WaitMinimum + 무작위(0 ~ RandomRange)초
그다음    = 직전 대기 × 2 + 무작위(0 ~ RandomRange)초
RepeatTimes 번 두 배가 된 뒤에는 같은 간격으로 계속 (포기하지 않음)
```

설정 키는 OCPP 설정의 `Internal` 칸에 있는 `RetryBackoffWaitMinimum`, `RetryBackoffRandomRange`, `RetryBackoffRepeatTimes`이다. 기본값은 3 / 10 / 3이다. 11/06의 9, 21, 48, 97은 3+6, 9×2+3, 21×2+6, 48×2+1로 이 식에 그대로 맞는다.

| 안 | 값 | 간격 예 | 최대 |
|---|---|---|---|
| 기본 | 3 / 10 / 3 | 9 → 21 → 48 → 97 … | 약 174초 |
| **B (채택)** | **3 / 5 / 2** | 5 → 13 → 28 → 28 … | **약 47초** |
| C | 3 / 3 / 1 | 4 → 10 → 10 … | 약 15초 |

무작위 값을 넣는 이유가 있다. 서버가 죽었다 살아날 때 충전기 수백 대가 같은 순간에 몰려 접속하지 않게 하려는 것이다. 충전기가 많은 현장도 생각해서 B로 했다. 비밀 값이 아니므로 git으로 관리하는 기본 설정 `ocpp-config-sc6.json`에 넣었다.

### 3-1. 서버로 가는 길만 막기

11/06에는 WiFi 자체를 끊었다. 그러면 원격 SSH도 같이 끊긴다. 이번에는 **서버 주소로 가는 경로만** 막았다.

```sh
ip route add blackhole 192.168.45.139/32    # 서버로 가는 패킷만 버림
sleep 120
ip route del blackhole 192.168.45.139/32
```

스크립트가 중간에 멈춰도 경로가 꼭 풀리게 `trap ... EXIT`를 걸었다.

```text
12:00:29                                         서버 경로 막음
12:00:46 Connection not successful ...           ← 17초 뒤 알아챔 (WebSocketPingInterval 10초)
12:00:53 Attempting reconnect after a wait of: 7000ms     3 + 4
12:01:08 ... 15000ms                                      7×2 + 1
12:01:43 ... 34000ms                                      15×2 + 4
12:02:17 ... 34000ms                                      여기서 고정
12:02:29                                         경로 풂
12:02:51 OCPP client successfully connected
```

다시 연결되자 BootNotification 없이 StatusNotification만 보냈다. 같은 프로그램 안에서 다시 접속한 것이라 규격대로다.

### 3-2. 오프라인 충전은 그대로

서버가 끊겼을 때 새 충전을 허용할지도 정리했다. 판단 순서는 libocpp `authorize_id_token()`에 있다.

1. `LocalAuthorizeOffline`이 켜져 있으면, 서버가 내려준 로컬 목록과 최근 승인 기억(AuthorizationCache)에서 카드를 찾는다.
2. 그래도 없으면 `AllowOfflineTxForUnknownId`가 켜져 있을 때만 아무 카드나 받는다.

| 안 | 오프라인에서 |
|---|---|
| **1. 지금 (모두 끔)** | **충전 안 함.** 무단 충전은 없지만, 서버 장애 = 충전소 전체 정지 |
| 2. 아는 카드만 | 전에 승인된 카드는 충전 |
| 3. 아무 카드나 | 장애 중에도 영업, 대신 미과금 위험 |

이것은 기술이 아니라 운영 정책이라서 기획 쪽 답이 올 때까지 1로 둔다.

## 4. 중간 이미지와 새 SD 회귀 시험

지금까지 보드에서 쓰던 sc6-bsp, sc6-meter는 손으로 복사한 파일이었다. 이번에 이미지에 넣었다.

```bitbake
# sc6-image.bb
#   sc6-bsp, sc6-meter (11/10 중간 이미지): /usr/bin 과 /etc/default 설정만 넣는다.
#   자동 시작(systemd 서비스)은 아직 없음 - M7-6 에서 설계자 확인 뒤 추가
IMAGE_INSTALL += "sc6-bsp sc6-meter"
```

실행 스크립트 `run-m7-bsp.sh`도 바꿨다. m7 폴더에 실행 파일이 있으면 그것을 쓰고, 없으면 이미지의 `/usr/bin` 것을 쓴다. 개발 중에는 새 파일만 복사해서 시험하고, 평소에는 이미지 것으로 돈다.

### 4-1. 백업 먼저

새 SD에는 레이어에 들어 있는 것만 들어간다. 보드에서 손으로 바꾼 것을 먼저 챙겼다.
- WiFi 설정
- 시험용 CA 인증서
- 시험 보드용 `EM_ACTIVE=high`
- `/home/root/m7` 폴더 (서버 비밀번호가 든 user config 포함)

비밀번호가 들어 있으므로 묶음 파일은 git이 아니라 빌드 PC의 권한 700 폴더에만 두었다.

### 4-2. 빈 카드는 쓰기를 거부당했다

SD 기록 스크립트(`sc6-tfa-sd.sh raw`)가 바로 멈췄다. 이 스크립트는 카드 전체를 덮어쓴다. 그래서 장치 이름을 잘못 넣는 사고를 막으려고, 1·2번 파티션 라벨이 `fsbl1`, `fsbl2`이고 `metadata1`이 있는 카드에만 쓴다. 즉 **예전에 SC6 이미지를 쓴 카드**만 받는다. 새로 꺼낸 카드는 FAT32 파티션 하나뿐이니 거부가 맞다.

처음 한 번만 같은 순서를 손으로 실행했다.

```sh
sudo umount /dev/sdc1
sudo dd if=FlashLayout_sdcard_stm32mp157a-sc6-opteemin.raw of=/dev/sdc bs=8M conv=fdatasync status=progress
sync
sudo sfdisk --relocate gpt-bak-std /dev/sdc     # 이미지 끝의 백업 GPT 를 카드 끝으로
sudo blockdev --rereadpt /dev/sdc
```

### 4-3. 확인 스크립트 하나로

회귀 확인 항목을 `check-fresh-sd.sh`에 모았다. 읽기만 하고, 비밀 파일은 권한만 보고 내용은 출력하지 않는다.

| 항목 | 결과 |
|---|---|
| 패키지 | sc6-bsp 1.0-r0.5, sc6-meter 1.0-r0.1, everest-core (libocpp 패치 포함) |
| `60-wlan.network` | `RequiredForOnline=routable` 들어 있음 |
| 실패한 서비스 | 없음 |
| 비밀 파일 | 600, `wpa_passphrase`가 남기는 `#psk=` 원문 줄 없음 |
| 자동 시작 | 없음 (의도대로) |
| 서버 | 연결됨 |

### 4-4. 첫 부팅의 NTP 322초는 함정이었다

[11/06에 고친 NTP]({% post_url 2026-11-06-sc6-ntp-networkd-online-state %})를 이번에는 보드에서 손댄 설정 없이 이미지만으로 확인하려 했다. 그런데 첫 부팅에서 시각 서버에 처음 연결된 시점이 **부팅 후 322초**였다.

이유는 간단했다. 새 카드에는 WiFi 비밀번호가 없다. 시리얼 콘솔에서 WiFi를 손으로 넣은 시점이 그 무렵이었다. 네트워크가 그때 생겼으니 NTP도 그때 됐다. 다시 부팅하니 결과가 달랐다.

```text
[   15.15] Starting Network Time Synchronization...
[   25.43] systemd-timesyncd: Contacted time server 216.239.35.0:123 (time1.google.com).
```

**25초.** 새 카드의 첫 부팅은 사람이 개입한 부팅이라 회귀 시험의 기준이 될 수 없다.

### 4-5. 그 밖에 본 것

- **`everest.service`가 enabled로 보인다.** EVerest 패키지에 원래 들어 있는 서비스다. `ConditionFileNotEmpty=/etc/everest/config.yaml` 조건이 붙어 있어서, 그 파일이 없으면 건너뛴다. 자동 시작은 M7-6에서 우리 서비스로 따로 만든다.
- **이미 닫힌 거래가 한 번 더 닫혔다.** 처음 EVerest를 켜자 거래 18번 StopTransaction(PowerLoss)이 다시 나갔다. 백업을 뜰 때 보드 OCPP DB에 그 거래가 아직 열려 있었고, 그 DB가 그대로 복원됐기 때문이다. 서버는 이미 닫힌 거래라 그냥 받아 넘겼다. 제품의 백업·복원에서는 OCPP DB를 빼는 편이 낫겠다.
- **충전과 heartbeat:** 거래 19번으로 충전 한 사이클과 heartbeat 4초 시험(2-6 표의 마지막 줄)을 했다. 이미지에 든 `/usr/bin/sc6-bsp`로 통과했다.

## 5. 정리

### 커밋

```text
meta-sc6  5ef00cd M8: sc6-bsp EVerest heartbeat 감시 (r0.5), 이미지에 sc6-bsp·sc6-meter 포함
sc6-work  8949643 M8: heartbeat·재접속 시험 스크립트, OCPP 재접속 간격 B안, 이미지 빌드 검사
sc6-work  5c6c60c M8: 새 SD 회귀 확인 스크립트, 빈 카드에 SD 이미지 쓰는 안내
```

### 오늘 배운 것

1. **"하드웨어가 없으니 무시"를 다시 보자.** heartbeat는 하드웨어 기능이 아니라 **상대가 죽었는지 아는 유일한 방법**이었다.
2. **안전 상태로 가는 것보다 돌아오는 것이 어렵다.** 상대가 바뀔 때만 명령을 보내는 구조라면, 회복할 때 "마지막으로 받은 명령"을 기억해 두어야 한다. 그러지 않으면 둘의 생각이 어긋난 채로 굳는다.
3. **감시가 둘이면 경계를 시험하자.** BSP 3초, EVerest 5초. 그 사이(4초)를 얼려야 BSP 혼자 하는 복원을 볼 수 있다. 그리고 그 경계는 타이밍에 따라 흔들린다.
4. **원격 시험은 창 하나 기준으로 만들자.** 한 번 실행하면 끝나는 스크립트가 결과도 깔끔하다.
5. **끊김 시험은 SSH를 살려 두고.** `ip route add blackhole`이면 서버만 끊을 수 있다.
6. **첫 부팅은 기준이 아니다.** 사람이 손댄 부팅의 시각 기록으로 판단하면 안 된다. 다시 부팅해서 봐야 한다.
