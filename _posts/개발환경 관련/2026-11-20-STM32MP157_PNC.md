어제(11/19) ISO 15118 디지털 통신과 K-VAS가 됐다. 다음 질문은 "EVerest는 PnC(Plug & Charge)도 되나"였다. 케이블만 꽂으면 차가 인증서로 스스로를 증명하고 결제까지 끝나는 방식이다. 결론부터 쓰면 **소프트웨어는 이미 다 있고, 남은 일은 인증서와 서버**였다.

| 일 | 결과 |
|---|---|
| 시험용 인증서 | V2G 루트 → 충전기, MO 루트 → 계약(EMAID `KRKNV100000001A`), OEM 까지 한 벌 |
| PC 시뮬레이션 | 빌드 PC에 PC용 EVerest를 빌드(8분). TLS → 계약 인증서 검증 → 인증 → 충전 → 종료 |
| SteVe 연동 | OCPP PnC를 켜야 PnC가 제안됨. 켜면 SteVe가 PnC 인증(DataTransfer)을 거절 |
| 오프라인 | 충전기 자체 검증 + 로컬 승인 목록으로 충전됨. 목록에 없으면 거절 |
| 실제 보드 + EV3 | 5 % PWM에서 SLAC → EV3가 TLS 요청 → 우리 인증서에 `unsupported_certificate` → 카드로 기본 충전 |
| EV3가 믿는 루트 | 우리 것도, Hubject 아시아 루트도 아님. 국가 PnC 루트로 추정 |

## 1. EVerest에는 이미 다 있었다

보드에 올라간 everest-core 패키지의 모듈 설명(manifest)을 훑었다. PnC에 필요한 설정이 모두 들어 있었다.

| 모듈 | PnC 관련 설정 | 지금 값 |
|---|---|---|
| `EvseManager` | `payment_enable_contract` (PnC 결제) | 꺼짐 |
| `EvseV2G` | `tls_security`, `verify_contract_cert_chain` | TLS 금지 |
| `EvseSecurity` | V2G 루트, 충전기 인증서·키 보관 위치 | 인증서 없음 |
| OCPP 1.6 | `ISO15118PnCEnabled`, `ContractValidationOffline` | 꺼짐 |

하나 더 알게 된 것. `Evse15118D20`(ISO 15118-20) 설명에 **-20은 TLS 전용**이라고 적혀 있다. 충전기 인증서가 없으면 -20은 제안 목록에서 조용히 빠진다. 12월 말까지 해야 할 -20 대응에도 인증서가 필요하다는 뜻이라, PnC 실험이 헛일이 아니다.

## 2. 시험용 인증서 한 벌

PnC에는 인증서 사슬이 세 갈래 필요하다.

```text
V2G 루트 ── CPO 중간 1 ── CPO 중간 2 ── 충전기(SECC)     ← TLS 서버 인증서
MO 루트  ── MO 중간 1  ── MO 중간 2  ── 계약(EMAID)      ← 차가 내는 "회원 카드"
OEM 루트 ── OEM 중간 1 ── OEM 중간 2 ── 차량 제조사 인증서
```

EVerest 소스에도 시험용 인증서가 들어 있지만, 비밀키까지 공개된 것이라 쓰지 않았다. 빌드 PC에 받아 둔 Josev(ISO 15118 파이썬 구현)의 생성 스크립트를 복사해 새로 만들었다. 바꾼 것은 둘이다. 충전기 인증서 유효기간을 60일에서 365일로, 계약 ID를 `KRKNV100000001A`로. 비밀번호는 무작위로 만들어 권한 600 파일에만 두었다.

```text
충전기(SECC) <- V2G 루트   OK
계약 <- MO 루트            OK
차량 OEM <- OEM 루트       OK
SECC 키 <-> 인증서         짝 맞음
```

## 3. PC에서 PnC를 끝까지

보드 이미지에는 파이썬이 없어서 차량 시뮬레이터(`PyEvJosev`)를 보드에서 돌릴 수 없다. 그래서 빌드 PC에 **PC용 EVerest**를 따로 빌드했다. 원본 소스는 건드리지 않고 빌드 폴더만 따로 두었다(out-of-tree). 32코어라 8분 걸렸다.

구성은 보드와 같은 `EvseV2G`, AC 단상 220 V로 맞추고 카드(EIM)는 꺼서 PnC가 아니면 충전이 안 되게 했다. 차량 쪽은 Josev, CP와 SLAC는 시뮬레이터다.

```text
SupportedAppProtocol → SessionSetup → ServiceDiscovery
→ PaymentServiceSelection   SelectedPaymentOption: Contract
→ PaymentDetails            Validation of the contract certificate was successful!
→ Authorization             "authorization_type": "PlugAndCharge", "type": "eMAID"
→ ChargeParameterDiscovery → PowerDelivery → ChargingStatus ×33 → SessionStop
```

PnC 흐름이 규격 순서 그대로 끝까지 갔다. 이 단계의 인증은 "항상 승인" 시험 모듈이었으니, 확인한 것은 **TLS와 인증서 사슬**까지다.

## 4. SteVe에 붙였더니

### 4-1. OCPP 설정이 PnC를 끈다

시험 서버 SteVe를 붙이자 PnC가 아예 제안되지 않았다. 차는 카드 방식을 골랐고, 카드가 없으니 인증만 기다리다 끝났다. 소스를 보니 OCPP 모듈이 `ISO15118PnCEnabled` 값으로 충전기의 PnC를 켜고 끈다. **OCPP를 쓰는 한, 충전기 설정이 아니라 OCPP 설정이 PnC 스위치다.** 지금 보드 설정(false)으로는 PnC가 나올 수 없다.

덤으로 SteVe가 8180 포트를 HTTPS로만 받는다는 것도 다시 만났다(11/6 보안 프로파일 2 작업). 시뮬레이션 충전기도 보드처럼 wss + 비밀번호로 붙였다.

### 4-2. SteVe는 PnC 인증을 모른다

`ISO15118PnCEnabled`를 켜자 충전기는 계약 인증을 OCPP 1.6 PnC 확장 방식, 즉 `DataTransfer`에 담아 보냈다.

```text
충전기 → SteVe  DataTransfer  vendorId=org.openchargealliance.iso15118pnc  messageId=Authorize
SteVe 로그      Cannot process DataTransfer ... Operation is not implemented
SteVe → 충전기  {"status":"Rejected"}
```

충전기 쪽은 할 일을 다 했고, **서버가 PnC를 구현하지 않았다.** 온라인 PnC를 끝까지 보려면 다른 서버가 필요하다.

### 4-3. 오프라인이면 된다

libocpp에는 서버가 끊겼을 때의 경로가 있다. 충전기가 계약 인증서를 직접 검증하고, 로컬 승인 목록에서 계약 ID를 찾는다. 서버 주소를 닫힌 포트로 바꿔 처음부터 오프라인으로 만들었다. 로컬 목록은 서버가 `SendLocalList`로 내려 줬다고 가정하고 시뮬레이션 DB에 직접 넣었다.

| 시험 | 결과 |
|---|---|
| 목록에 계약 ID 있음 | `Local contract validation result: Valid` → `Offline: contract Valid` → 충전 34 Wh |
| 목록 비움 (대조) | 인증서는 Valid인데 **REJECTED**, 충전 안 함 |

오프라인 거래는 StartTransaction, MeterValues, StopTransaction으로 대기열에 쌓였다. 다시 접속하면 올라가야 하는데, 여기서 하나 걸렸다. SteVe는 접속 1~2 ms 뒤 무조건 GetConfiguration을 먼저 보낸다. PC 시뮬레이션에서는 libocpp가 이것을 "연결 전" 상태로 받고 그 뒤로 BootNotification을 보내지 않았다. 세 번 다 같았고 빈 DB로도 같았다. 같은 SteVe 로그에서 **보드는 같은 1 ms 간격에도 정상**이었다. 빠른 PC의 경합으로 보이지만 원인은 아직 모른다. 오프라인 정책에서 재접속 업로드는 핵심이라 보드에서 꼭 다시 볼 항목이다.

## 5. 실제 보드와 EV3

시험 차가 Tesla에서 기아 EV3로 바뀌었다. 우리 시험용 루트를 EV3가 알 리 없으니 PnC가 될 것이라 기대하지는 않았다. 대신 **실제 차가 PnC를 어떻게 시도하는지** 보기로 했다. 보드에는 충전기 몫 인증서만 넣고(계약·OEM 키는 넣지 않음), 기존 인증서 폴더는 통째로 백업했다.

### 5-1. 1차: 아무 일도 없었다

꽂았는데 74초 동안 SLAC조차 시작되지 않았다. 로그에 `Set PWM On`이 없었다. 어제 Tesla 때처럼 `ac_hlc_use_5percent: false`(정격 PWM)였는데, 이 설정에서 충전기는 **인증을 받은 뒤에야 PWM을 켠다.** 어제는 카드를 대서 PWM이 켜졌고, 오늘은 대지 않았다. 차는 PWM이 보여야 통신을 시작한다.

PnC는 꽂은 뒤 통신으로 인증하는 방식이니 인증 전에 통신부터 열어야 한다. ISO 15118-3은 이것을 **5 % PWM**으로 한다.

### 5-2. 2차: 5 %로 바꾸자

```text
16:50:40  Set PWM On (5.0%)
16:50:43  SLAC MATCHED (감쇠 24 dB)
16:50:48  SDP security 0x00 → "SDP requested TLS, announcing TLS"
16:50:48  trusted_ca_keys: no configured chain matched
16:50:48  SSL_accept ... error:0A000413        ← 경고 43 unsupported_certificate
16:50:48  D-LINK_ERROR → PWM Off → X1 → E/F(4초) → 인증 대기
16:54:54  카드 → "HLC disabled ... nominal PWM" → 53.3 % → 충전 → 정상 종료
```

패킷(`tcpdump -U`)을 빌드 PC로 가져와 TLS 첫 메시지를 직접 풀었다(파이썬 표준 라이브러리만으로 짠 작은 분석기).

| 방향 | 내용 |
|---|---|
| EV3 → 충전기 | ClientHello: TLS 1.2, `ECDHE-ECDSA-AES128-SHA256`, `ECDH-ECDSA-AES128-SHA256`, secp256r1 — ISO 15118-2 규정 그대로 |
| | `trusted_ca_keys`: 믿는 루트 **1개**를 공개키 SHA-1 해시로 알려 옴 |
| 충전기 → EV3 | ServerHello, 우리 인증서 사슬, ServerKeyExchange |
| EV3 → 충전기 | fatal alert `unsupported_certificate` |

EV3는 PnC를 시도하는 차이고, 믿는 루트가 정확히 하나다. 실패하면 카드로 기본 충전이 된다.

## 6. 그 루트는 누구 것인가

EV3가 보낸 해시를 우리 시험 루트, EVerest 시험 루트, Josev 시험 루트와 대조했다. 모두 아니었다. 해시를 검색해도 나오는 것이 없었다.

Hubject는 지역별 V2G 루트를 공개한다. 아시아 루트(`V2G Asia Root CA G1`)는 신청 양식을 거쳐야 받을 수 있어서 직접 받아 대조했다. 공개키 해시, SPKI 해시, 인증서 해시 세 방식 모두 **불일치**였다. 계산이 맞는지는 그 인증서의 Subject Key Identifier가 SPKI 해시 끝부분과 RFC 5280 방식대로 맞아떨어지는 것으로 확인했다.

남은 유력 후보는 **국가 PnC 루트**다. 올해 기사들을 모으면 이렇다.

| 시점 | 내용 |
|---|---|
| 2026-07 | 현대차그룹이 2021년부터 운영하던 PnC 인증서와 발급 권한을 기후에너지환경부·한국환경공단에 무상 이관 (MoU) |
| 2026-10-01 | 국가 PnC 인증체계 공개·시연 |
| ~2026-12 | 공공 충전기 시범서비스 (채비가 첫 시범 사업자, 급속 30기) |
| 2027-02 | 정식 서비스 목표 |

EV3는 현대차그룹 차량이다. 확정은 그 루트를 받아 대조해야 한다.

무공해차 통합누리집(ev.or.kr)의 한국환경공단 "PnC 안내"에 국가 방식이 나와 있었다. **충전기는 ISO 15118-2 + OCPP 1.6 PnC 확장**, 충전기 인증서는 **충전사업자(CPO)의 서버가 V2G PKI에서 발급**받는 구조다. 오늘 우리가 시뮬레이션으로 확인한 구조와 같다. 다만 제조사가 참여하거나 인증서를 신청하는 공개 절차는 아직 없다. 공식 창구는 같은 사이트의 민원·문의 게시판이다.

## 7. 정리

### 커밋

```text
sc6-work  4c10b9b  실험실 PnC: 시험용 인증서, PC 시뮬레이션 빌드·실행, SteVe 연동, 오프라인 시험
sc6-work  c81548f  보드 PnC 시험 (실제 차량 EV3): TLS 요청 확인, 시험 인증서 거부, 카드로 기본 충전
sc6-work  (이 글)  루트 인증서 trusted_ca_keys 해시 대조 스크립트, 블로그
```

같은 날 오전에는 어제 글의 "덤"을 풀었다. 계량기 모듈이 0x0120 판이라 배율이 달랐다(전류 /100, 전력 /1, 누적 /3.2). 5분 충전 약 530 Wh로 맞아떨어졌다. 화면에 충전량·전력·전류·전압·시간을 뿌리는 구조도 넣었다.

```text
meta-sc6  c4c5775  sc6-meter: 계량기 모듈 0x0120 판 배율
meta-sc6  1671410  sc6-hmi: 충전 데이터를 화면 VP 로
meta-sc6  0d7d112  sc6-hmi.default: 충전량·전력을 유니코드 문자 소수 2자리(u2)로
```

### 배운 것

1. **"되나?"는 소스 설정 목록부터 본다.** PnC에 필요한 것은 EVerest에 다 있었다. 남은 일은 코드가 아니라 인증서와 서버였다.
2. **스위치가 어디에 있는지 확인한다.** 충전기 설정에서 PnC를 켜도 OCPP 설정이 꺼져 있으면 꺼진다. 위층 설정이 아래층을 덮는다.
3. **실패도 정보다.** EV3는 거절하면서 자기가 믿는 루트를 알려 줬다. TLS 첫 메시지 한 개가 "국내 PnC 인증서 체계가 어디냐"는 질문의 단서가 됐다.
4. **같은 규격 안에서도 설정이 충돌한다.** K-VAS는 정격 PWM을 권하고, PnC는 5 % PWM이 필요하다. 제품 설정에서 둘을 함께 정해야 한다.
5. **대조 시험을 붙인다.** 오프라인 충전이 된 것만으로는 왜 됐는지 모른다. 목록을 비우고 거절되는 것까지 봐야 근거가 선다.
