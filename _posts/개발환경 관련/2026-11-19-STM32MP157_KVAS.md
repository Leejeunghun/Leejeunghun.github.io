지금까지의 충전은 모두 IEC 61851 기본 충전이었다. 충전기는 CP 신호의 PWM으로 "최대 몇 A까지 써도 된다"만 알려 주고, 차의 상태는 알 수 없다. 국내에서는 화재 예방을 위해 충전 중 배터리 정보를 받는 규격(K-VAS, 스마트 제어 충전기 배터리 정보교환 프로토콜)이 생겼다. 이 규격은 ISO 15118 디지털 통신 위에서 동작한다. 오늘(11/19)은 그 바닥부터 올라갔다.

| 일 | 결과 |
|---|---|
| ISO 15118-2 AC 충전 | Tesla Model 3와 PLC 짝 맺기 → 디지털 통신 충전 → 정상 종료 |
| K-VAS 서비스 제공 | EVerest에 이미 있는 VAS 모듈로 서비스 정의 |
| 막힌 곳 1 | 차가 "충전 서비스만" 물어서 K-VAS가 응답에서 빠짐 → EvseV2G 패치 |
| 막힌 곳 2 | 차가 IP 주소를 잘못 읽음 → 주소를 4자리 묶음으로 |
| 막힌 곳 3 | 시험용 수신 도구가 IPv6를 못 받음 → K-VAS 수신 프로그램 작성 |
| 결과 | 3초마다 배터리 정보 61개 수신 (SoC 68→69 %, 팩 최대 17 A) |
| 덤 | 전력량계가 실제 전력의 약 3분의 1만 기록 |

## 1. 바닥은 이미 있었다

### 1-1. PLC 모뎀

ISO 15118은 충전 케이블의 CP선 위에 PLC(HomePlug Green PHY) 신호를 얹어 통신한다. SC6 보드에는 QCA7005 PLC 모뎀이 있고, 10월에 리눅스 드라이버와 부팅 때 펌웨어를 올리는 서비스를 만들어 두었다. ST 이미지로 옮긴 뒤에도 그대로 들어 있는지부터 확인했다.

```text
eth0 드라이버: qcaspi                     ← PLC 모뎀이 리눅스 네트워크 장치로
eth0 IPv6: fe80::4b:4eff:fe56:2           ← ISO 15118 통신에 쓰는 링크 로컬 주소
qca7005-fw: MAC-QCA7005-3.3.0.31 running  ← 부팅 때 펌웨어 적재 완료
```

`eth0`의 MAC이 고정이라 IPv6 주소도 부팅마다 같다. 이것이 나중에 K-VAS에서 중요해진다.

### 1-2. EVerest 모듈

이미지에 들어간 everest-core 패키지를 풀어 보니 필요한 모듈이 다 있었다.

| 모듈 | 하는 일 |
|---|---|
| `EvseSlac` | 차와 PLC 짝 맺기 (ISO 15118-3) |
| `EvseV2G` | ISO 15118-2 / DIN 70121 통신 |
| `StaticISO15118VASProvider` | 부가 서비스(VAS)를 yaml 파일로 정의해 `EvseV2G`에 제공 |
| `Evse15118D20` | ISO 15118-20 (다음 단계) |

구성 파일에서 꺼져 있었을 뿐이다. 그래서 제품 구성은 그대로 두고, 이 모듈들을 켠 **시험 구성 파일을 따로** 만들었다. 시험 스크립트는 EVerest 서비스를 멈추고 시험 구성으로 띄운 뒤, Ctrl+C를 누르면 원래 서비스로 되돌린다.

## 2. Tesla와 디지털 통신 충전

K-VAS 규격은 AC에서 PWM을 5 %로 바꾸지 말고 정상 듀티를 유지하라고 권고한다. 그래야 디지털 통신이 안 되는 차도 기본 충전으로 그대로 충전된다. 그래서 `ac_hlc_use_5percent: false`로 두었다.

```text
09:47:46.7  꽂음 → PWM 53.3 % (32 A)
09:47:48~49 SLAC 짝 맺기 (2.7초, 감쇠 24 dB)
09:47:49.9  차 C 상태 → K1 ON, 기본 충전으로 먼저 시작
09:47:52.3  V2G 연결, ISO 15118-2 선택, 결제 방식 ExternalPayment (카드)
09:47:53.2  PowerDelivery(Start) → 디지털 통신 충전으로 전환
            ChargingStatus 약 0.23초마다
09:48:22.7  중지 버튼 → StopCharging 알림 → 차 PowerDelivery(Stop) → SessionStop
```

차를 꽂자마자 기본 충전으로 먼저 전류가 흐르고, 디지털 통신이 준비되면 그쪽으로 넘어간다. 규격이 허용하는 순서 그대로였다. 다만 AC ISO 15118-2 메시지에는 **SoC가 없다.** 충전 상태 요청(ChargingStatusReq)은 내용이 비어 있다. 그래서 K-VAS가 따로 TCP로 배터리 정보를 받는 것이다.

## 3. K-VAS: 세 번 막혔다

K-VAS 흐름은 이렇다.

```text
① 차: 어떤 서비스가 있나요?            (ServiceDiscoveryReq)
② 충전기: 충전 + 61000 "Battery data VAS Korea"
③ 차: 61000 자세히                     (ServiceDetailReq)
④ 충전기: 파라미터 세트 31000 = TCP Socket, 충전기 IP, 포트, 3초
⑤ 차: 61000 쓸게요                     (PaymentServiceSelectionReq)
⑥ 차가 그 IP/포트로 TCP 연결 → 3초마다 배터리 정보 프레임
```

②와 ④는 EVerest의 VAS 모듈에 yaml 파일 하나로 정의했다. 로그에는 `Loaded VAS configuration with 1 services`가 찍혔다. 그런데 차는 ③을 보내지 않았다.

### 3-1. 차가 "충전 서비스만" 물었다

V2G 메시지는 EXI(이진 XML)라서 로그로는 내용을 알 수 없다. 처음에는 세션 기록에 남은 16진수 14바이트를 비트 단위로 손으로 풀었고, 나중에 Wireshark의 V2G 해석 플러그인(dsV2Gshark)으로 확인했다.

```xml
<ServiceDiscoveryReq>
  <ServiceCategory>EVCharging</ServiceCategory>
</ServiceDiscoveryReq>
```

Tesla는 처음부터 "충전 서비스만 알려 달라"고 묻는다. EVerest `EvseV2G`는 ISO 15118-2 규칙대로 요청한 종류만 응답에 넣고, K-VAS(종류 `OtherCustom`)는 빼 버렸다. 응답 길이는 VAS가 없을 때와 똑같은 27바이트였다.

여기서 "Tesla는 K-VAS를 지원하지 않는다"고 결론을 냈었다. **틀린 결론이었다.** 같은 차를 다른 국내 충전기에서 잡은 캡처를 받아 보니, 그 충전기는 같은 요청에도 61000을 응답에 넣었고 Tesla는 그것을 보고 ③~⑥을 그대로 진행했다. K-VAS 규격도 충전기가 61000을 응답에 넣으라고 정하고 있다. 그래서 `EvseV2G`를 고쳤다.

```diff
-        if (req->ServiceCategory_isUsed and req->ServiceCategory != service.ServiceCategory)
+        if (req->ServiceCategory_isUsed and req->ServiceCategory != service.ServiceCategory and
+            service.ServiceID != KVAS_BATTERY_DATA_SERVICE_ID)
             continue;
```

다른 서비스는 그대로 거르고 61000만 예외로 둔다. 소스 트리는 건드리지 않고, libocpp 패치 때처럼 레시피에 패치 파일로 붙였다. 다시 시험하자 Tesla가 ServiceDetail을 묻고 61000/31000을 선택했다.

### 3-2. 차가 IP 주소를 잘못 읽었다

선택까지 했는데 TCP 연결이 오지 않았다. 패킷을 보니 Tesla가 이상한 주소를 찾고 있었다.

```text
우리가 알려 준 주소:  fe80::4b:4eff:fe56:2
Tesla가 찾는 주소:    fe80::4b:4eff:fe56:2:ffff   (Neighbor Solicitation 4번, 아무도 답하지 않음)
```

우리 주소 표기는 규격상 맞는 축약형이다. 다만 `4b`, `2`처럼 앞자리 0을 뺀 묶음이 있다. 다른 충전기는 주소 묶음이 우연히 모두 4자리였다. Tesla의 해석기가 각 묶음을 4자리로 가정하는 것으로 보고, 같은 주소를 `fe80::004b:4eff:fe56:0002`로 채워 보냈다. Tesla는 바로 그 주소로 연결을 시도했다. 서비스 정의 파일 한 줄만 바꾼 것이라 빌드도 필요 없었다.

### 3-3. 받는 쪽이 IPv6를 몰랐다

이번에는 연결 요청(SYN)이 왔는데 보드가 즉시 거절(RST)했다. 시험용으로 띄운 busybox `nc`가 IPv4로만 기다리고 있었다. 어차피 정식 수신 프로그램이 필요하니 첫 버전(`sc6-kvas`)을 바로 만들었다.

- IPv6(+IPv4) 소켓으로 대기
- 3초마다 오는 TLV 프레임을 해석해 한 줄씩 출력하고 원본은 파일에 기록
- VIN 계열 항목은 개인정보라 **길이만** 출력

보드에 올리기 전에 다른 충전기 캡처의 실제 프레임 49개를 PC에서 흘려 보내, dsV2Gshark 해석 결과와 같은 값이 나오는지 먼저 확인했다.

### 3-4. 받았다

```text
16:16:53.947 연결 [Tesla]:49164
16:16:56.957 #1  SoC 68.0% SoH 100% 팩 361.1V  0.0A 셀 3.34/3.34V 온도 24/23℃ 암호화VIN 97B
16:17:02.965 #3  SoC 68.0% SoH 100% 팩 361.8V  8.4A 셀 3.34/3.34V 온도 24/23℃ 암호화VIN 32B
16:19:51.167 #59 SoC 69.0% SoH 100% 팩 364.6V 17.1A 셀 3.38/3.38V 온도 24/24℃ 암호화VIN 32B
16:19:56.659 연결 끝 (61번, 3,725바이트)
```

연결 3초 뒤 첫 프레임, 이후 정확히 3초 간격, 충전이 끝나자 차가 연결을 닫았다. 첫 프레임만 암호화 VIN에 차의 공개키가 붙어 97바이트이고, 이후는 32바이트다. 규격의 형식 그대로다.

## 4. 덤: 전력량계가 3분의 1만 센다

어제 시험 부하로 충전할 때 이상한 점이 있었다. 계량기의 순간 전력은 680 W인데, 누적 전력량은 1분에 35 Wh(약 2.1 kW)씩 올랐다. 어느 쪽이 맞는지 정할 기준이 없었는데, K-VAS가 그 기준을 줬다.

| | 값 |
|---|---|
| 차 배터리로 들어간 전력 (K-VAS) | 364.6 V × 17.0 A ≈ **6.2 kW** (충전기 입력으로는 약 6.7 kW) |
| 같은 3분 동안 계량기 누적 | 102 Wh, 평균 약 **2.0 kW** |

680 W 부하일 때도, 6 kW 넘게 받는 Tesla일 때도 누적은 늘 약 2 kW 속도였다. 계량기가 실제 전류를 따라가지 못한다. 서버로 가는 충전량(과금 기준)이 틀리는 문제라 하드웨어(CT 규격, 배선, 모듈 범위 설정)를 확인하기로 했다.

## 5. 정리

### 커밋

```text
meta-sc6  4e11461  everest-core: EvseV2G 가 K-VAS 배터리 정보 서비스(61000)를 항상 알리게 (패치 0002)
meta-sc6  b33cd44  sc6-kvas: K-VAS 배터리 정보교환 TCP 서버 1차 (받기·해석·기록)
sc6-work  ab25e8e  ISO 15118 / K-VAS 보드 시험: 시험 구성, K-VAS 서비스 정의, 시험·분석 스크립트 (11/19)
```

### 배운 것

1. **"안 된다"는 결론은 비교 대상을 보고 내린다.** 우리 충전기만 보고 "Tesla는 K-VAS를 모른다"고 했지만, 같은 차가 다른 충전기에서 된다는 캡처 한 개로 뒤집혔다.
2. **규격대로가 늘 정답은 아니다.** EvseV2G는 ISO 15118-2 규칙을 정확히 지켰고, 그래서 K-VAS가 안 됐다. 국내 규격이 그 위에 요구하는 것을 따로 맞춰야 했다.
3. **맞는 표기와 상대가 읽을 수 있는 표기는 다르다.** IPv6 축약 표기는 규격상 문제없었지만 상대 해석기가 못 읽었다. 현장에서 동작하는 다른 충전기의 표기를 따르는 것이 빨랐다.
4. **이진 프로토콜은 해석 도구부터 갖추자.** 로그에는 "ServiceDiscoveryRes 보냄"까지만 있었다. 패킷을 잡고 메시지를 풀어 보고서야 원인이 보였다.
5. **새 기능이 옛 문제의 기준이 될 수 있다.** K-VAS로 받은 배터리 전력 덕분에 계량기 문제를 숫자로 판정할 수 있었다.

### 남은 것

| 항목 | 내용 |
|---|---|
| 계량기 | CT 규격, 배선, 모듈 범위 설정 확인 (실제의 약 3분의 1 기록) |
| K-VAS 화면 | SoC만 화면에 표시 (규격상 다른 항목은 표시 금지) |
| K-VAS 제어 | 목표 SoC 설정, 도달하면 충전 정지 |
| K-VAS 운영 | 개인정보 동의 화면, 환경부 서버 전송 (전송 규격 문서 필요) |
| 제품 구성 | ISO 15118 기본 켜기, 공칭 전압 220 V, sc6-kvas 서비스화, 이미지 포함 |
| ISO 15118-20 | EvseV2G가 Evse15118D20으로 대체 예정. -20 VAS 대응 기한 2026-12-31 |
