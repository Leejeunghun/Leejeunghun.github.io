지난번에 Yocto Scarthgap으로 EVerest를 32비트 ARM용으로 빌드하는 데 성공했다. 남은 질문은 하나였다.

> **650MHz Cortex-A7 두 개로 EVerest가 충분히 빠른가?**

정석은 새 OS를 우리 보드에 이식(TF-A의 DDR 설정부터 U-Boot, 커널 DTS까지)한 뒤 재는 것이다. 하지만 이식에는 몇 주가 걸린다. 몇 주를 들였는데 "CPU가 모자라서 못 쓴다"는 결론이 나오면 곤란하다. 그래서 **며칠 안에 답을 얻는 지름길**을 먼저 택했다.

## 1. 아이디어: 커널은 그대로, 프로그램만 새것으로

리눅스에서 프로그램이 실행될 때 필요한 것은 크게 두 가지다.

- **커널**: 하드웨어를 다루고 시스템 호출을 받아 준다
- **사용자 공간**: 프로그램과 라이브러리(glibc, libstdc++, boost …)

이 둘은 시스템 호출이라는 약속으로만 연결된다. 그러니 **지금 보드의 커널(5.4) 위에서, 새로 빌드한 rootfs의 프로그램과 라이브러리를 그대로 쓸 수 있다.** `chroot`가 바로 그 일을 한다. 루트 디렉터리를 다른 곳으로 바꿔서, 그 안의 프로그램이 그 안의 라이브러리를 쓰게 한다.

```text
SD 카드 (16GB 중 1.5GB만 사용 중)
├── p1~p7  지금의 MYiR 시스템 (커널 5.4, 우리 DTB)   ← 이걸로 부팅, 건드리지 않음
└── p8     새 파티션: Scarthgap rootfs + EVerest      ← chroot 로 들어가서 실행
```

- 기존 시스템은 그대로라 위험이 없다. 시험이 끝나면 p8만 지우면 된다.
- 제품 구성이 아니라 **"이 칩에서 EVerest가 얼마나 무거운가"를 재는 시험**이다.

## 2. 첫 번째 관문: SD 카드 백업

지금 SD 카드에는 원본 이미지 이후에 넣은 것이 많다. SC6 DTB, QCA7005 펌웨어와 자동 적재 서비스, 블루투스 설정 등이다. 파티션을 건드리기 전에 통째로 백업하기로 했다.

### Windows에서는 장치가 안 보였다

처음에는 SD 카드를 기록할 때 썼던 Win32DiskImager로 반대로 읽으려 했다. 그런데 **Device 목록에 카드가 나오지 않았다.**

Win32DiskImager는 **드라이브 문자가 붙은 장치만** 보여 준다. 이 카드에는 리눅스 파티션(ext4)만 있어서 Windows가 드라이브 문자를 붙이지 않는다. 이때 "디스크를 포맷하시겠습니까?" 창도 뜨는데, 누르면 카드가 지워지니 반드시 취소해야 한다.

### 리눅스 빌드 PC에서 dd로

어차피 p8을 만들 때 리눅스 빌드 PC를 써야 하니 백업도 거기서 했다.

```bash
lsblk -o NAME,SIZE,MODEL,TRAN,MOUNTPOINT      # 15GB, usb 인 장치 = SD 카드
sudo umount /dev/sdc?* 2>/dev/null
sudo dd if=/dev/sdc bs=4M status=progress | gzip -1 > ~/sc6-sd-backup-20261029.img.gz
gzip -t ~/sc6-sd-backup-20261029.img.gz && echo OK
```

16GB를 통째로 읽지만 빈 공간은 압축이 잘 되어 파일은 작게 나온다.

## 3. 두 번째 관문: "kernel too old"를 피하기 — OLDEST_KERNEL

chroot 방식에는 함정이 하나 있다. glibc는 빌드할 때 **"최소 몇 버전 커널에서 돌 것인가"**를 정해 놓는다. Yocto에서는 이 값이 `OLDEST_KERNEL`이다. 보드 커널이 이 값보다 낮으면 새 rootfs의 모든 프로그램이 이렇게 거부된다.

```text
FATAL: kernel too old
```

그래서 빌드 전에 값부터 확인했다.

```bash
bitbake -e glibc | grep ^OLDEST_KERNEL=
# OLDEST_KERNEL="5.15"
```

**Scarthgap의 기본값은 5.15**였고, 보드 커널은 5.4다. 그대로였다면 빌드에 몇 시간을 쓰고 보드에서 실행조차 못 했을 것이다.

다행히 이 값은 Yocto가 정한 기본값일 뿐이다. glibc 2.39 자체는 커널 3.2까지 지원한다. `local.conf`에 낮춰 적고 이미지 구성도 함께 추가했다.

```bash
# B 방식: 보드 커널 5.4 위 chroot 실행용
OLDEST_KERNEL = "5.4"
IMAGE_INSTALL:append = " everest-core mosquitto bash procps"
IMAGE_FSTYPES:append = " tar.xz"
```

대가는 있다. glibc가 바뀌면 그 위의 모든 패키지가 다시 빌드된다.

```text
Sstate summary: Wanted 2569 Local 17 Mirrors 0 Missed 2552 Current 1303
```

**약 2,500개 작업을 다시 했다.**

## 4. 세 번째 관문: Ubuntu 24.04의 AppArmor

빌드를 시작하자마자 작업 8개가 같은 오류로 쓰러졌다.

```text
File ".../bitbake/bin/bitbake-worker", line 278, in child
    bb.utils.disable_network(uid, gid)
File ".../bitbake/lib/bb/utils.py", line 1694, in disable_network
    with open("/proc/self/uid_map", "w") as f:
PermissionError: [Errno 1] Operation not permitted
```

bitbake는 각 작업을 **네트워크가 막힌 격리 공간(user namespace)**에서 실행한다. 빌드 결과가 인터넷 상태에 따라 달라지지 않게 하려는 것이다. 그런데 **Ubuntu 24.04는 AppArmor로 일반 사용자의 user namespace 생성을 제한**한다. 격리 공간은 만들어지지만 권한이 빠진 상태라서 `uid_map`에 쓸 수 없다.

지난번 빌드 때는 괜찮았는데 이번에 막힌 것은, 그때 임시로 풀어 둔 설정이 재부팅으로 원래대로 돌아갔기 때문으로 보인다. 이번에는 영구로 풀었다.

```bash
sysctl kernel.apparmor_restrict_unprivileged_userns          # = 1 이면 이게 원인
echo 'kernel.apparmor_restrict_unprivileged_userns = 0' | sudo tee /etc/sysctl.d/60-bitbake-userns.conf
sudo sysctl --system
```

보안 강화 기능 하나를 끄는 것이지만 빌드 전용 PC에서는 흔히 쓰는 설정이다.

하나 더 있었다. 프롬프트 앞에 `(base)`가 붙어 있었는데, **conda 파이썬 환경이 켜진 상태**라는 뜻이다. Yocto는 시스템 파이썬을 기준으로 돌기 때문에 `conda deactivate`로 끄고 envsetup부터 다시 했다.

## 5. 네 번째 관문: 카드 리더가 흔들린다

빌드를 기다리는 동안 SD 카드에 p8을 미리 만들어 두었다.

```bash
sudo parted /dev/sdc unit MiB print free           # GPT 경고가 나오면 Fix
sudo parted /dev/sdc mkpart chroot ext4 <userfs 끝>MiB 100%
sudo mkfs.ext4 -L chroot /dev/sdc8
```

GPT 경고는 1.5GB짜리 이미지를 16GB 카드에 써서 "GPT 백업 헤더가 디스크 끝에 없다"는 내용이다. `Fix`를 고르면 된다.

빌드가 끝나서 rootfs를 풀려는데, 이번엔 **`/dev/sdc`가 사라져 있었다.** 다시 찾아보니 같은 카드가 `sdd`로 잡혀 있었고, 마운트하자 이렇게 나왔다.

```text
mount: /mnt/sd8: can't read superblock on /dev/sdd8.
```

dmesg에 이유가 다 있었다.

```text
[sdd] Sense Key : Illegal Request / Logical block address out of range
critical target error, dev sdd, sector 3145697 op 0x0:(READ)
EXT4-fs (sdd8): unable to read superblock
usb 1-3: USB disconnect, device number 32
usb 1-7-port1: disabled by hub (EMI?), re-enabling...
```

| 줄 | 의미 |
|---|---|
| `Logical block address out of range` | 카드 리더가 "그 주소는 없다"며 읽기를 거절함. 직전까지는 p8이 자동 마운트될 정도로 정상이었음 |
| `USB disconnect` | 카드 리더가 PC에서 빠졌다 붙음. `sdc` → `sdd`로 이름이 바뀐 이유 |
| `disabled by hub (EMI?)` | USB 허브 포트가 **전기 잡음으로 꺼졌다 켜짐**. 같은 허브의 무선 키보드·마우스 수신기도 다시 잡힘 |

**SD 카드나 빌드 결과의 문제가 아니라 카드 리더 연결이 불안정했던 것**이다. 슬롯이 여러 개인 멀티 리더(빈 슬롯이 `sdb 0B`로 보임)를 앞면 포트에 꽂아 쓰고 있었다.

교훈은 두 가지다.

- **카드 리더는 메인보드 뒷면 포트에 직접** 꽂는다.
- 장치 이름(`sdc`, `sdd` …)은 USB가 다시 연결될 때마다 바뀐다. **명령을 실행하기 전에 매번 `lsblk`로 확인한다.** 실제로 이 사이에 다른 USB 저장장치가 `sdc`라는 이름을 차지했다. 습관대로 `sdc`에 명령을 실행했다면 엉뚱한 장치를 건드릴 뻔했다.

p8은 다시 포맷하고 다시 풀었다.

### 어떤 tar.xz를 풀어야 하나

deploy 폴더에는 비슷한 이름의 파일이 여러 개 있다.

| 파일 | 사용 |
|---|---|
| `st-image-core-...rootfs.tar.xz` (날짜 없는 링크) | ✅ 최신 빌드를 가리킴 |
| `st-image-core-...rootfs-20261029xxxxxx.tar.xz` | ✅ 위 링크가 가리키는 실제 파일 |
| `st-image-core-...rootfs-20261026xxxxxx.tar.xz` | ❌ 지난번 빌드 (EVerest 없음, 5.15 기준) |
| `st-image-bootfs/userfs/vendorfs-...` | ❌ 다른 파티션용 |

```bash
readlink -f .../st-image-core-openstlinux-weston-stm32mp1.rootfs.tar.xz   # 20261029 가 보이면 OK
sudo tar xpf <위 파일> -C /mnt/sd8 --numeric-owner
file /mnt/sd8/usr/bin/manager
```

```text
ELF 32-bit LSB pie executable, ARM, EABI5 ... for GNU/Linux 5.4.0 ...
```

**`for GNU/Linux 5.4.0`**. `OLDEST_KERNEL`이 적용되어 보드 커널에서 돌 수 있는 바이너리가 됐다.

## 6. 보드에서 실행

SD 카드를 보드에 다시 꽂고 부팅했다. 기존 시스템이 평소대로 떴고, `/dev/mmcblk1p8`이 보였다. WSL에서 미리 만들어 둔 시험 묶음(`board-test.tar.gz`)을 보냈다.

| 파일 | 역할 |
|---|---|
| `board-chroot.sh` | p8 마운트 + proc/sys/dev/dev/pts 바인드 + tmp/run tmpfs, `mount / enter / umount` |
| `config-sil-board.yaml` | 보드 측정용 구성. 가상 차량의 ISO 15118(Java+Python 약 180MB) 제거, HLC 끔, **시작 6초 뒤 32A 단상 충전 자동 시작** |
| `run-everest.sh` | chroot 안에서 mosquitto + EVerest manager 실행 |
| `measure.sh` / `measure_cpu.sh` | 메모리(PSS) / CPU(구간 측정) |

```bash
sh /home/root/board-test/board-chroot.sh mount
sh /home/root/board-test/board-chroot.sh enter
bash /root/everest-test/run-everest.sh
```

```text

[INFO] manager :: Config loading completed in 644ms
[INFO] manager :: Starting 16 modules
[INFO] manager :: 🚙🚙🚙 All modules are initialized. EVerest up and running [3608ms] 🚙🚙🚙
[INFO] connector_1:Evs :: 🌀🌀🌀 Ready to start charging 🌀🌀🌀
[INFO] connector_1:Evs :: EVSE IEC Session Started: EVConnected
[INFO] connector_1:Evs :: EVSE IEC EIM Authorization received
[INFO] connector_1:Evs :: EVSE IEC Set PWM On (53.3%) took 0 ms

[INFO] connector_1:Evs :: IEC allow_power_on forwarded to BSP: true

```

**Cortex-A7 650MHz에서 EVerest가 떴고, 충전 흐름이 처음부터 끝까지 돌았다.**

- 모듈 16개 초기화에 **3.6초**. 모듈들이 동시에 뜨면서 각자 2.0~2.8초가 걸렸다.
- PWM 53.3%는 32A 알림이다(53.3 × 0.6 = 32A). 보드의 CP 하드웨어로 그대로 나갈 값이다.
- 첫 실행이라 설정을 DB로 옮기는 단계가 있어 충전 상태까지 약 15초가 걸렸다.

몇 가지 경고는 시험 구성 탓이라 무시했다.

| 메시지 | 이유 |
|---|---|
| `Running in chroot, ignoring command 'is-active'` | 어떤 모듈이 `systemctl is-active`를 부르는데 chroot 안이라 무시됨 |
| `Could not find ... V2G_ROOT_CA.pem`, `TLS is disabled` | 인증서 없음 → Plug&Charge 비활성. 지금은 HLC를 끈 기본 AC 충전이라 무관 |
| `DEPRECATED MODULE` (API, EvAPI) | 시뮬레이션(SIL)용 모듈이 곧 없어진다는 예고 |

## 7. 측정 결과

시리얼 콘솔이 하나뿐이라 SSH 창을 하나 더 열어 같은 chroot에 들어가 측정했다.

### 메모리

```text
프로세스 17개  RSS 합계 156 MB  PSS 합계 50 MB
```

```text
               total        used        free      shared  buff/cache   available
Mem:             425         140         137           9         165         284
```

| 항목 | 보드 (ARM 32비트) | WSL (x86 64비트) 같은 구성 |
|---|---|---|
| EVerest PSS 합계 | **50 MB** | 124 MB |
| 보드 available | 330 → **284 MB** | — |

RSS 합계는 공유 라이브러리를 프로세스마다 중복해서 세므로 실제보다 크다. 실제 사용량에 가까운 PSS로 보면 50MB다. 32비트라 포인터가 작아서 WSL보다 훨씬 작게 나왔다. **메모리는 걱정할 필요가 없다.**

### CPU — 시험 스크립트부터 고쳐야 했다

```text
measure_cpu.sh: line 6: getconf: command not found
awk: cmd. line:1: Division by zero
```

`measure_cpu.sh`는 `/proc/<pid>/stat`의 utime+stime이 10초 동안 늘어난 양을 틱 단위로 잰다. 이를 퍼센트로 바꾸려면 초당 틱 수(`getconf CLK_TCK`)가 필요하다. 그런데 이미지를 최소로 만들었더니 **`getconf`가 없었다.** ARM 리눅스의 기본값인 100을 쓰도록 고쳤다. 제품에도 들어갈 MQTT 브로커(mosquitto)도 합계에 넣었다.

```bash
HZ=$(getconf CLK_TCK 2>/dev/null) || HZ=100   # 보드 rootfs 에는 getconf 가 없다. ARM 리눅스는 100
pids="$(descendants "$root") $(pgrep -x mosquitto)"
```

`measure.sh`가 보여 주는 `ps`의 %CPU는 **시작 이후의 평균**이라 초기화 부하가 섞인다. 그래서 충전 중의 10초 구간만 따로 재는 것이 정확하다.

```text
PID     NAME                            CPU%
1655    manager                          0.0
1672    api:API                          2.8
1674    connector_1:Evs                  4.4
1675    connector_1_pow                  2.8
1676    energy_manager:                  6.5
1677    error_history:E                  0.8
1686    ev_api:EvAPI                     1.5
1689    ev_manager:EvMa                  1.3
1696    grid_connection                  1.9
1702    persistent_stor                  0.6
1708    setup:Setup                      1.6
 ...    (나머지 6개 0.1 이하)

-----------------------------------------------
합계 31.3% (코어 1개 기준, 10초 구간)
```

**코어 1개 기준 31.3%, 즉 코어 2개(200%) 중 약 16%**를 쓴다.

| 구분 | 모듈 | CPU% |
|---|---|---|
| 제품에도 들어감 | mosquitto (MQTT 브로커) | 6.9 |
| | energy_manager (전류 배분, 주기 실행) | 6.5 |
| | connector_1 (EvseManager, 충전 상태 관리) | 4.4 |
| | 나머지 (인증, 오류 기록, 설정 등) | 약 5 |
| 시험용, 제품에서 빠짐 | API, 가상 보드(YetiSimulator), ev_manager, ev_api, SLAC 시뮬레이터 | 약 8.4 |

| 항목 | 결과 |
|---|---|
| 같은 구성 WSL(i7-13620H) | 8.3% |
| 보드(Cortex-A7 650MHz) | 31.3% → **약 4배** |
| 시험용 모듈을 뺀 추정 | 약 23% |
| load average | 0.75 |
| SoC 온도 | 48.9 °C |

미리 정한 기준(30% 미만이면 여유 충분, 30~80%면 쓸 수 있음)으로는 경계에 걸쳐 있다. 하지만 시험용 모듈이 빠지고, mosquitto와 energy_manager는 메시지 주기로 더 줄일 여지가 있다. **이 칩으로 EVerest를 쓸 수 있다**고 판단했다.

## 8. 정리

| 질문 | 답 |
|---|---|
| 32비트 Cortex-A7용으로 빌드되는가 | ✅ (10/26) |
| 커널 5.4 위에서 실행되는가 | ✅ `OLDEST_KERNEL = "5.4"`로 빌드하면 됨 |
| 메모리는 충분한가 | ✅ PSS 50MB, 남은 메모리 284MB |
| CPU는 충분한가 | ✅ 충전 중 31%/200% |

**보드 이식(A 방식)으로 넘어간다.** 이 작업은 이제 "될지 안 될지 모르는 몇 주"가 아니라 "되는 걸 아는 몇 주"가 됐다.

아직 재지 않은 부하도 있다.

- **ISO 15118 고수준 통신(HLC)과 TLS.** 특히 TLS 연결을 맺을 때 순간적으로 CPU를 많이 쓴다.
- **OCPP** 서버 통신
- 시뮬레이터 대신 들어갈 **실제 BSP 모듈** (CP PWM, ADC, 릴레이)

이 셋은 이식이 끝난 뒤 실제 구성에서 다시 잰다.

### 오늘 배운 것

- **chroot는 "이식 전 실측"에 좋은 지름길이다.** 커널과 사용자 공간이 시스템 호출로만 연결된다는 점을 이용하면, 부트로더와 커널을 건드리지 않고 새 사용자 공간의 성능을 미리 볼 수 있다.
- **새 rootfs를 옛 커널에 올릴 때는 `OLDEST_KERNEL`부터 확인한다.** 빌드를 몇 시간 돌리기 전에 확인할 수 있는 한 줄이다.
- **Ubuntu 24.04 빌드 PC는 AppArmor의 user namespace 제한을 풀어야 한다.** 재부팅 뒤에도 유지되도록 `/etc/sysctl.d`에 적는다.
- **USB 카드 리더는 생각보다 자주 흔들린다.** 장치 이름은 매번 `lsblk`로 확인하고, 쓰기가 끝나면 `umount && sync` 후 dmesg로 오류가 없었는지 본다.
- **`ps`의 %CPU는 평균값이다.** 실제 동작 중의 부하는 `/proc/<pid>/stat`의 차이로 구간을 재야 한다.
