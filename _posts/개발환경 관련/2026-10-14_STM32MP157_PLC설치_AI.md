[지난 글](#)에서 PLC가 충전기에서 어떤 역할을 하는지, QCA7005가 어떻게 부팅하는지 개념을 정리했다. 이번 글은 그 개념을 실제 보드에서 하나씩 확인해 나간 기록이다.

시작할 때 상태는 이랬다.

```console
root@myir:~# lsmod | grep qca
qcaspi                 24576  0
qca_7k_common          16384  1 qcaspi
```

모듈은 올라갔는데 사용 카운트가 `0`이었다. "드라이버가 칩에 안 붙었구나" 생각하고 원인을 찾기 시작했다.

## 1. 붙지 않은 게 아니었다

SPI 핀부터 봤다.

```console
pin 400 (PZ0): device 44004000.spi function analog group PZ0
pin 401 (PZ1): device 44004000.spi function analog group PZ1
pin 402 (PZ2): device 44004000.spi function analog group PZ2
```

SPI 핀이 `af5`가 아니라 `analog`였다. 사용 카운트 0에 핀까지 analog이니 바인딩 실패라고 확신했다. 그런데 SPI 버스를 직접 보니 얘기가 달랐다.

```console
root@myir:~# ls /sys/bus/spi/devices/
spi0.0

root@myir:~# dmesg | grep -iE "spi|qca"
qcaspi spi0.0: ver=0.2.7-i, clkspeed=8000000, burst_len=5000, pluggable=0
qcaspi spi0.0: Using random MAC address: 62:d3:bd:18:1a:f3
qcaspi spi0.0 eth1: SPI thread created
```

`eth1`이 이미 만들어져 있었다. **처음부터 붙어 있었던 것이다.** 판단 근거로 삼은 두 가지가 모두 잘못 읽은 것이었다.

| 본 것 | 내가 읽은 뜻 | 실제 뜻 |
|---|---|---|
| `lsmod` 사용 카운트 0 | 디바이스가 안 붙음 | **다른 모듈이 이 모듈을 참조하는 수.** 네트워크 드라이버는 디바이스가 붙어도 0일 수 있음 |
| SPI 핀 `analog` | 핀이 설정 안 됨 | SPI가 쉬는 동안 **runtime PM이 핀을 sleep 상태로 내려둔 것** |

### eth1이 있다는 것 자체가 증거다

`pluggable=0`이 중요하다. 이 모드에서는 드라이버가 probe할 때 칩의 시그니처 레지스터를 읽는다.

```c
/* drivers/net/ethernet/qualcomm/qca_spi.c */
if (!qcaspi_pluggable) {
	qcaspi_read_register(qca, SPI_REG_SIGNATURE, &signature);
	if (signature != QCASPI_GOOD_SIGNATURE) {      /* 0xAA55 */
		dev_err(&spi->dev, "Invalid signature (0x%04X)\n", signature);
		return -EFAULT;
	}
}
register_netdev(...)                               /* → eth1 */
```

`0xAA55`가 안 읽히면 `eth1`은 생기지 않는다. 그러니 `eth1`이 있다는 것만으로 **SPI 배선, SPI 모드(CPOL/CPHA), 클럭, 칩 리셋 핀 극성**이 모두 맞다는 게 증명된다. 보류해뒀던 "Q_RST 극성 확인" 항목이 이걸로 닫혔다.

### 인터럽트도 확인

시그니처 읽기는 폴링이라 인터럽트 없이도 된다. 실제 데이터를 주고받으려면 Q_INT(PG7) 인터럽트가 동작해야 한다.

```console
root@myir:~# cat /sys/kernel/debug/eth1/info
Sync state       : 2 (QCASPI_SYNC_READY)
INTR REQ         : 982
INTR SVC         : 982
SPI mode         : 3

root@myir:~# grep eth1 /proc/interrupts
120:        981          0  stm32gpio   7 Edge      eth1

root@myir:~# grep "(PG7)" /sys/kernel/debug/pinctrl/*50002000*/pinconf-pins
pin 103 (PG7): input - low - floating
```

인터럽트가 981번 들어왔고 전부 처리됐다. 982와 981이 하나 차이 나는 건 드라이버가 인터페이스를 올릴 때 첫 동기화를 시작하려고 카운터를 1에서 시작하기 때문이다.

```c
qca->intr_req = 1;    /* netdev open 시 */
qca->intr_svc = 0;
```

PG7이 `input`으로 나온 것도 의미가 있다. 이 핀은 벤더 핀맵에서 LCD 클럭(`LCD_CLK`)이던 핀이다. [U-Boot에서 LCD 패널을 끈 작업](#)의 효과가 여기서도 확인됐다.

## 2. 칩에게 직접 물어보기

`eth1`이 칩과 동기화됐다고 해서 칩이 PLC 모뎀으로 동작한다는 뜻은 아니다. 칩에게 직접 상태를 물어봐야 한다.

보드에는 PLC 관리 도구가 없었다. 대신 파이썬이 있어서, 펌웨어 버전을 묻는 관리 메시지(`VS_SW_VER.REQ`)를 raw 소켓으로 직접 만들어 보냈다.

```python
LOCAL_DEV = bytes.fromhex("00b052000001")   # "바로 옆 QCA 칩" 전용 주소
ETH_P_HPAV = 0x88E1                         # HomePlug 관리 메시지

req = LOCAL_DEV + src + struct.pack("!H", ETH_P_HPAV)
req += bytes([0x00]) + struct.pack("<H", 0xA000) + OUI   # MMV, MMTYPE, OUI
s.send(req.ljust(60, b"\x00"))
```

칩이 대답했다.

```console
from     : 00:b0:52:00:00:01
status   : 0x00
deviceid : 0x06
version  : BootLoader
```

통신은 완벽하게 됐다. 그런데 **칩이 PLC 펌웨어가 아니라 부트로더 상태였다.** 차와 통신할 수 없는 상태라는 뜻이다.

## 3. 고장이 아니라 설계였다

부트로더에 머무는 이유는 둘 중 하나다. 칩 옆 플래시가 비어 있거나, 플래시가 아예 없거나. 넷리스트를 열었다.

```xml
<net name="unconnected-(U8-SPI_CLK-Pad67)"> ... pintype="passive+no_connect"
<net name="unconnected-(U8-SPI_CS-Pad65)">  ... pintype="passive+no_connect"
<net name="unconnected-(U8-SPI_DI-Pad3)">   ... pintype="passive+no_connect"
<net name="unconnected-(U8-SPI_DO-Pad66)">  ... pintype="passive+no_connect"
```

QCA7005의 플래시 쪽 SPI 핀이 전부 미연결이었다. 부품 목록에도 플래시 칩이 없었다. **플래시리스(host boot) 설계**다. 칩은 펌웨어를 스스로 읽어올 곳이 없으니, 매번 MPU가 내려주기를 부트로더 상태로 기다린다.

이걸 알고 나니 필요한 게 명확해졌다.

1. **펌웨어 파일** — Qualcomm 독점 파일이라 공급사에서 받아야 한다
2. **올려주는 도구** — open-plc-utils

## 4. open-plc-utils 크로스 빌드

Qualcomm이 공개한 HomePlug 관리 도구 모음이다. 커널이나 U-Boot 빌드 때는 에러가 줄줄이 나왔는데, 이번엔 한 번에 통과했다.

빌드 설정 파일을 먼저 봤다.

```makefile
# make.def
CC=$(CROSS)gcc
AR=$(CROSS)ar
```

컴파일러를 `$(CROSS)` 접두어로 조립하는 단순한 구조다. 빌드 중에 호스트에서 실행하는 도구도 없다. 지난번 U-Boot에서 고생한 GLIBC 문제나 sysroot 오염 문제가 생길 여지가 없었다.

```bash
. /opt/st/myir/3.1-snapshot/environment-setup-cortexa7t2hf-neon-vfpv4-ostl-linux-gnueabi
make CROSS=arm-ostl-linux-gnueabi- CC="$CC" ROOTFS="$HOME/work/plc_out" install
```

`CC`에 SDK의 `$CC`를 넘기는 게 핵심이다. 거기에 하드플로트 ABI와 sysroot 옵션이 들어 있다.

```console
$ echo $CC
arm-ostl-linux-gnueabi-gcc -mthumb -mfpu=neon-vfpv4 -mfloat-abi=hard -mcpu=cortex-a7 --sysroot=...
```

make.def의 `CC=$(CROSS)gcc`는 커맨드라인 값에 덮어써진다. `CROSS`만 넘기면 컴파일러는 ARM용이 되지만 하드플로트 옵션과 sysroot가 빠진다.

결과를 확인했다.

```console
$ file plcboot
plcboot: ELF 32-bit LSB executable, ARM, EABI5, interpreter /lib/ld-linux-armhf.so.3
```

`ld-linux-armhf.so.3`가 보이면 보드와 같은 하드플로트 ABI로 제대로 빌드된 것이다.

빌드 로그에 `error`가 108번 찍혀서 잠깐 놀랐는데, 전부 `error.o`라는 **파일 이름**이었다.

```text
arm-ostl-linux-gnueabi-gcc ... -o efbu efbu.o getoptv.o ... error.o ...
```

도구 109개가 디버그 정보 포함 14MB였다. strip해서 2.3MB로 줄이고 하나로 묶어 보드에 올렸다.

```console
root@myir:~# plctool -i eth1 -r local
eth1 00:B0:52:00:00:01 Request Version Information
eth1 00:B0:52:00:00:01 QCA7005 BootLoader
```

정식 도구로도 같은 대답이 왔다. 파이썬에서 숫자(`0x06`)로만 보였던 칩 종류가 `QCA7005`로 풀려서 나왔다.

## 5. 펌웨어 패키지

공급사에서 받은 파일은 세 개였다.

| 파일 | 크기 | 정체 |
|---|---|---|
| `MAC-QCA7000-QCA7005-GP-v3.3.0.0031-00-X-CS.nvm` | 399KB | 런타임 펌웨어 |
| `QCA7005-EVSE-SpiSlave-Automotive.pib` | 9.8KB | **충전기용·SPI 슬레이브** 설정 |
| `NvmSoftloader.nvm` | 20KB | softloader |

PIB 파일 이름이 우리 보드 구성을 그대로 말해준다. 충전기(EVSE) 역할이고, MPU와 SPI 슬레이브로 연결되고, 차량 등급이다.

softloader는 쓸지 말지 소스로 확인했다.

```c
/* plc/plcboot.c */
if (plc.SFT.file == -1)
{
	if (_anyset (plc.flags, PLC_FLASH_DEVICE))
		error (1, ECANCELED, "No Softloader file named");
}
```

softloader는 **플래시 기록 옵션(`-F`)을 쓸 때만** 필요하다. 플래시가 없는 우리 보드는 RAM에 바로 올리므로 필요 없다. 공급사가 표준 패키지로 묶어 준 것이다.

## 6. plcboot — 실패라고 했는데 성공이었다

이번 작업에서 제일 헷갈린 부분이다. 실패 메시지가 세 번 나왔고, 셋 다 원인이 달랐다.

### 첫 번째: "No Parameter file named"

```console
plcboot: No Parameter file named: Operation canceled
```

PIB 파일을 안 넘겼다는 뜻이다. 명령을 `\`로 줄바꿈해서 붙여넣었는데, 첫 줄만 실행된 것이다. 한 줄로 바꿔서 다시 했다.

### 두 번째: 파일이 없다

```console
ls: cannot access '*.nvm': No such file or directory
```

도구 묶음만 보드로 보내고, 펌웨어 파일 두 개는 안 보냈다. 단순한 실수였다.

### 세 번째: 타임아웃

파일을 다 보내고 실행했다.

```console
plcboot: WriteExecuteFirmware2: Read timeout or network error

eth1 00:B0:52:00:00:01 QCA7005 BootLoader
```

펌웨어를 쓰는 단계에서 칩의 응답이 끊겼고, 직후 확인하니 여전히 부트로더였다. 이번엔 진짜 실패라고 생각했다.

의심한 건 드라이버였다. `qcaspi`는 칩과 동기화를 잃으면 칩을 리셋한다.

```c
/* qca_spi.c */
netdev_dbg(qca->net_dev, "sync: resetting device.\n");
spi_config |= QCASPI_SLAVE_RESET_BIT;
```

펌웨어가 시작되는 순간 동기화가 잠깐 끊기면 드라이버가 칩을 리셋할 수 있고, 플래시가 없으니 방금 올린 펌웨어가 날아간다. 시나리오가 맞아 보였다.

그런데 이 메시지가 `netdev_dbg`라서 기본 설정의 `dmesg`에는 안 나온다. 커널에 dynamic debug가 켜져 있어서 잠깐 열어봤다.

```bash
echo 'module qcaspi +p' > /sys/kernel/debug/dynamic_debug/control
```

그리고 다시 `plcboot`를 실행하니 이번엔 다른 에러가 나왔다.

```console
eth1 00:B0:52:00:00:01 Bootloader must be running
```

`plcboot`는 칩이 정확히 `"BootLoader"`라고 대답할 때만 진행한다.

```c
if (strcmp (firmware, "BootLoader"))
	Failure (&plc, "Bootloader must be running");
```

**칩이 이제 부트로더가 아니라는 뜻이다.** 디버그 로그에도 단서가 있었다.

```text
qcaspi spi0.0 eth1: Tx-ing packet: Size: 0x00000046
qcaspi spi0.0 eth1: qcaspi_receive: SPI_REG_RDBUF_BYTE_AVA: Value: 00000137
```

부트로더의 버전 응답은 108바이트였는데 이번 응답은 311바이트였다. 그리고 `sync: resetting device`는 없었다. 확인했다.

```console
root@myir:~# plctool -i eth1 -r local
eth1 00:B0:52:00:00:01 Request Version Information
eth1 00:B0:52:00:00:01 QCA7005 MAC-QCA7005-3.3.0.31-00-20231004-CS
```

**펌웨어가 돌고 있었다.** 세 번째 시도는 실패가 아니었다.

### 무슨 일이 있었나

```text
plcboot이 마지막 조각에서 "실행" 지시
  → 칩이 확인 응답을 보내기 전에 펌웨어로 넘어감
  → plcboot은 응답을 못 받고 "타임아웃" 보고
  → 펌웨어는 몇 초에 걸쳐 기동
  → 바로 뒤에 실행한 plctool은 그 틈에 실행되어 "BootLoader" 응답
```

드라이버가 칩을 리셋한다는 의심도 틀렸다. 펌웨어는 처음부터 정상적으로 올라가고 있었고, 내가 너무 일찍 확인했을 뿐이다.

> 도구가 "실패"라고 말해도 실제로 실패했는지는 별개다. `plcboot`는 응답을 못 받은 걸 실패로 보고했지만, 칩은 응답할 틈도 없이 다음 단계로 넘어간 것이었다.

이건 자동화할 때 바로 영향이 있다. 부팅 스크립트가 `plcboot`의 종료 코드만 보면, 성공했는데도 실패로 처리한다. **`plctool -r`을 몇 초 동안 반복하면서 `BootLoader`가 아니게 되는 걸로 판정**해야 한다.

## 7. 부팅할 때마다 자동으로

보드를 재부팅하자 예상대로 원래 상태로 돌아갔다.

```console
root@myir:~# plctool -r
eth1 00:B0:52:00:00:01 QCA7005 BootLoader
```

플래시리스 설계라 펌웨어는 RAM에만 있었고, 전원이 꺼지면서 사라졌다. 그래서 부팅할 때마다 다시 올려주는 systemd 서비스를 만들었다.

### 스크립트 설계

앞에서 얻은 교훈을 그대로 반영했다.

```sh
# qcaspi 드라이버가 만든 인터페이스를 찾는다 (eth1 이라는 이름에 의존하지 않음)
find_iface() {
	for n in /sys/class/net/*; do
		drv=$(readlink "$n/device/driver" 2>/dev/null)
		case "$drv" in
		*/qcaspi) basename "$n"; return 0 ;;
		esac
	done
	return 1
}

# 칩 상태: bootloader | running | none(무응답)
chip_state() {
	out=$(plctool -i "$IFACE" -r local 2>&1)
	case "$out" in
	*BootLoader*) echo bootloader ;;
	*MAC-QCA*)    echo running ;;
	*)            echo none ;;
	esac
}
```

흐름은 이렇다.

1. `qcaspi` 인터페이스가 생길 때까지 기다린다
2. 칩이 응답할 때까지 기다린다
3. **이미 펌웨어가 돌고 있으면 아무것도 하지 않고 끝낸다** — 몇 번을 실행해도 안전하다
4. `plcboot`로 올리고, **종료 코드는 무시한 채** `plctool -r`을 최대 15초 반복해서 판정한다. 안 되면 3번까지 다시 시도한다

4번이 6절의 교훈이다. `plcboot`가 실패라고 해도 실제로는 성공했을 수 있으니, 칩의 대답으로 판단한다.

서비스는 단순한 oneshot이다.

```ini
[Unit]
Description=QCA7005 PLC firmware load (flashless host boot)
After=systemd-modules-load.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/qca7005-fwload.sh
TimeoutStartSec=180

[Install]
WantedBy=multi-user.target
```

펌웨어 파일은 `/lib/firmware/qca7005/`로 옮겼다. 홈 디렉터리에 두고 쓰던 걸 정식 위치로 정리한 것이다.

### 묶음을 만들다 한 번 멈칫한 것

스크립트, 서비스, 펌웨어를 보드의 `/`에 한 번에 풀 수 있게 tar로 묶었다. 처음엔 이렇게 묶었다.

```bash
tar czf qca7005-fw.tar.gz -C stage .
```

목록을 보니 파일만이 아니라 디렉터리 항목까지 들어가 있었다.

```text
drwxr-xr-x root/root  ./
drwxr-xr-x root/root  ./etc/
drwxr-xr-x root/root  ./lib/
...
```

이걸 보드의 `/`에 풀면 기존 `/`, `/etc`, `/lib`의 권한과 시간 정보가 묶음 쪽 값으로 덮어써진다. 파일만 명시해서 다시 묶었다.

```bash
tar czf qca7005-fw.tar.gz -C stage \
	usr/local/sbin/qca7005-fwload.sh \
	etc/systemd/system/qca7005-fw.service \
	lib/firmware/qca7005/*.nvm \
	lib/firmware/qca7005/*.pib
```

없는 상위 디렉터리는 tar가 알아서 만들고, 이미 있는 디렉터리는 건드리지 않는다.

### 첫 시험 — 건너뛰었다

설치하고 `reboot`로 재부팅했더니 서비스가 이렇게 끝났다.

```text
qca7005-fw: eth1: 이미 펌웨어 실행 중 - 건너뜀
```

성공은 했는데 펌웨어를 올리지 않았다. 재부팅 직전에 서비스를 손으로 한 번 실행해서 펌웨어를 올려뒀는데, `reboot`는 MPU만 재시작할 뿐 보드 전원을 끊지 않는다. 그 사이 QCA7005가 펌웨어를 그대로 들고 있었던 것으로 보인다.

결국 **확인하려던 "부트로더에서 자동으로 올리는 경로"는 실행되지 않았다.** 칩을 확실히 부트로더로 만들려면 전원을 끊어야 한다.

### 전원을 껐다 켜서 다시

```console
root@myir:~# journalctl -u qca7005-fw -b -l --no-pager
01:40:28 systemd[1]: Starting QCA7005 PLC firmware load (flashless host boot)...
01:40:32 qca7005-fw: eth1: 펌웨어 적재 시도 1
01:40:33 Write .../MAC-QCA7000-QCA7005-GP-v3.3.0.0031-00-X-CS.nvm (1) (00000040:7104)
01:40:33 Start .../MAC-QCA7000-QCA7005-GP-v3.3.0.0031-00-X-CS.nvm (1) (000000C0)
01:40:33 Write .../QCA7005-EVSE-SpiSlave-Automotive.pib (1) (00200000:9796)
01:40:33 Write .../MAC-QCA7000-QCA7005-GP-v3.3.0.0031-00-X-CS.nvm (5) (002CDD30:367784)
01:40:35 Start .../MAC-QCA7000-QCA7005-GP-v3.3.0.0031-00-X-CS.nvm (5) (002CE120)
01:40:36 MAC-QCA7005-3.3.0.31-00-20231004-CS is running
01:40:36 qca7005-fw: eth1: 완료 - eth1 00:B0:52:00:00:01 QCA7005 MAC-QCA7005-3.3.0.31-00-20231004-CS
01:40:36 systemd[1]: Started QCA7005 PLC firmware load (flashless host boot).
```

이번엔 처음부터 끝까지 다 보였다. 로그를 풀면 `plcboot`가 실제로 하는 일이 그대로 드러난다.

| 로그 | 하는 일 |
|---|---|
| `Write ...nvm (1) (00000040:7104)` → `Start (1)` | 펌웨어 파일 안의 작은 모듈(7KB)을 먼저 올려 실행 — 초기화 단계 |
| `Write ...pib (00200000:9796)` | PIB를 `0x00200000`에 기록 |
| `Write ...nvm (5) (002CDD30:367784)` | 펌웨어 본체(약 360KB) 기록 |
| `Start (5) (002CE120)` | 펌웨어 실행 지시 |
| `... is running` | 칩이 펌웨어로 대답 |

`.nvm` 파일 하나 안에 모듈이 여러 개 들어 있고, `plcboot`는 그중 필요한 것을 골라 순서대로 올린다는 것도 여기서 보인다.

전체가 **약 4초** 걸렸고, 부팅 시작부터 계산해도 14초 만에 모뎀이 준비됐다.

### 타임아웃이 재현되지 않았다

눈여겨볼 건 이번엔 `plcboot`가 **타임아웃 없이 `is running`까지 정상으로 끝났다**는 점이다. 6절에서 겪은 타임아웃은 매번 나는 현상이 아니었다.

그래서 스크립트를 종료 코드가 아니라 칩의 실제 상태로 판정하게 만든 게 더 의미가 있다. 타임아웃이 나는 날에도, 안 나는 날에도 같은 방식으로 맞게 판정한다. 원인을 다 밝히지 못한 불안정한 동작이 있으면, 그 동작에 기대지 않는 쪽으로 설계하는 게 맞다.

### 남는 문제 — 재부팅해도 칩은 리셋되지 않는다

첫 시험에서 드러난 사실이 하나 남는다. `reboot`로는 QCA7005가 리셋되지 않는 것으로 보인다. 충전기에서는 이게 문제가 될 수 있다. 칩이 재부팅 전 상태를 그대로 들고 있으면, 예를 들어 이전 충전에서 맺은 네트워크 키(NMK)가 남은 채로 새 소프트웨어가 시작된다.

깨끗하게 시작하려면 부팅할 때 Q_RST(PC3)로 칩을 한 번 리셋하는 게 맞다. 그런데 지금 DTS에서는 이 핀을 `gpio-hog`로 HIGH에 고정해두어서 유저 공간에서 토글할 수 없다. 다음에 손볼 항목이다.

## 정리

이번 작업은 처음부터 끝까지 **보이는 것과 실제가 계속 달랐다.**

1. `lsmod` 사용 카운트 0, SPI 핀 analog → **드라이버는 처음부터 붙어 있었다**
2. `eth1`이 생기고 칩과 동기화됨 → **칩은 부트로더 상태였다**
3. 칩이 부트로더 → **고장이 아니라 플래시리스 설계였다**
4. `plcboot`가 타임아웃으로 실패 보고 → **펌웨어는 정상적으로 올라갔다**
5. 자동 적재 서비스가 성공 → **실제로는 펌웨어를 올리지 않고 건너뛰었다**

매번 한 단계 더 들어가서 확인했을 때만 실제 상태가 보였다. 4번은 실패 메시지를 믿고 원인을 더 찾았다면 멀쩡히 동작하는 걸 고치려고 했을 것이고, 5번은 `SUCCESS`만 보고 넘어갔다면 정작 중요한 경로를 시험하지 않은 채 끝냈을 것이다.

도구의 판단을 그대로 받아들이기 전에, **그 판단이 무엇을 근거로 나왔는지**까지 확인하는 습관이 이번에도 결정적이었다.
