지난주까지의 결론은 이랬다. EVerest를 쓰려면 OS부터 바꿔야 하고, 메모리는 충분해 보이며, 남은 질문은 **"32비트 ARM에서 빌드되는가"**와 **"650MHz에서 충분히 빠른가"** 두 개다.

오늘은 첫 번째 질문에 답하러 갔다. 회사의 다른 리눅스 PC에서 **처음으로 Yocto로 OS 전체를 빌드**했다.

## 1. 지금까지는 OS를 빌드한 적이 없었다

정리하다 보니 새삼스러운 사실이 하나 있었다. 지금까지 우리는 OS를 한 번도 빌드하지 않았다.

```text
[MYiR 완성 이미지] SD 카드에 기록 (OpenSTLinux 3.1, Dunfell, 2021-11-25 빌드)
        │
        └─ 우리가 따로 빌드한 것만 교체
             ├ 커널 DTB, 커널 모듈   (WSL + MYiR SDK)
             ├ U-Boot               (LTDC 끄기)
             └ PLC 도구, 서비스      (손으로 복사)
```

커널 이미지조차 MYiR가 2021년 11월에 빌드한 것을 그대로 쓰고 있었다. 우리가 바꾼 건 DTB, 모듈, U-Boot뿐이다.

| | 지금까지 | 오늘 |
|---|---|---|
| 만드는 것 | 부품 몇 개 | **OS 전체** (TF-A, U-Boot, 커널, 모든 라이브러리, 이미지) |
| 기반 | MYiR 이미지 (Dunfell, 커널 5.4) | ST OpenSTLinux v6 (Scarthgap, 커널 6.6) |
| 컴파일러 | MYiR SDK의 gcc 9.3 | Yocto가 직접 만든 컴파일러 |
| 재현 | 손으로 한 작업 목록에 의존 | 레시피로 언제든 똑같이 |

## 2. 지금 SD 카드는 어디서 왔나

빌드 전에 가이드에 "만든 이미지를 SD 카드에 올리는 법"을 넣으려다, 정작 **지금 SD 카드를 어떻게 만들었는지 기억이 나지 않았다.** 흔적을 따라갔다.

다운로드 폴더에 이 파일이 있었다.

```text
C:\Users\USER\Downloads\FlashLayout_sdcard_stm32mp157c-ya157c-512d-v3-trusted.raw   1,536MB  2026-09-09
```

그리고 STM32CubeProgrammer의 설정 파일에 마지막으로 연 폴더가 남아 있었다.

```text
readFileLastPathWB=C:\myir-image-ubuntu18\flashlayout_myir-image-ubuntu18\trusted
```

그 폴더에는 7월에 받은 **Ubuntu 18.04 패키지**와 배치표(`.tsv`)가 있었다. 두 후보를 보드에서 확인한 사실과 맞춰 봤다.

| 지금 SD 카드 | Ubuntu 패키지 (CubeProgrammer) | `.raw` (9월) |
|---|---|---|
| 배포판 `openstlinux-eglfs` | ✘ Ubuntu 18.04 | ✔ |
| `userfs` 파티션 246MB 있음 | ✘ 배치표에 없음 | ✔ |
| 파티션 합계 약 1.5GB | ✘ rootfs만 2.6GB | ✔ 1,536MB |

**지금 SD 카드는 9월의 `.raw`로 만든 것**이었다. 14.9GB 카드에서 1.5GB만 쓰고 있던 이유도 여기 있었다. 통짜 이미지를 그대로 쓰면 이미지 크기만큼만 파티션이 잡힌다. CubeProgrammer는 7월에 Ubuntu로 시도할 때 썼고, 그 결과는 나중에 덮어쓴 것으로 보인다.

두 방법은 이렇게 다르다.

| | STM32CubeProgrammer | 이미지 기록 도구 |
|---|---|---|
| 연결 | 보드에 SD를 꽂은 채 **USB로 보드에 연결** | SD를 **PC 카드 리더**에 꽂음 |
| 입력 | `.tsv` + 파티션별 파일 | `.raw` 통짜 이미지 |
| 보드 설정 | 부트 스위치를 USB 부팅으로 | 필요 없음 |
| 대상 | SD 또는 eMMC | SD만 |

`.raw`는 CubeProgrammer로 쓸 수 없으니, 9월에는 Win32 Disk Imager 같은 도구로 쓴 것이다. 이 내용은 SD 카드 기록 문서에 남겨 뒀다.

### Ubuntu였다면 EVerest가 됐을까

잠깐 이런 생각도 들었다. 그때 Ubuntu로 갔다면 `apt`로 편하게 EVerest를 깔 수 있지 않았을까? 아니었다. Ubuntu 18.04는 Dunfell(2020)보다도 오래된 2018년 배포판이다. 지난주 WSL 빌드에서 걸렸던 **`libsystemd>=238`** 조건부터 통과하지 못한다(18.04는 systemd 237). 둘 다 EVerest에는 부족하고, 그중엔 지금 것이 더 새것이다.

## 3. 빌드 환경

| 항목 | 값 |
|---|---|
| PC | 별도 리눅스 PC, 32스레드 |
| ST 태그 | `openstlinux-6.6-yocto-scarthgap-mpu-v26.06.10` (STM32MPU ecosystem 6.2.1) |
| 작업 폴더 | `~/stm32mp`, 캐시 `~/yocto-cache` (다운로드·sstate를 빌드 폴더 밖에) |
| 설정 | `MACHINE=stm32mp1`, `DISTRO=openstlinux-weston` |

```bash
mkdir -p ~/stm32mp && cd ~/stm32mp
repo init -u https://github.com/STMicroelectronics/oe-manifest.git \
  -b refs/tags/openstlinux-6.6-yocto-scarthgap-mpu-v26.06.10
repo sync
DISTRO=openstlinux-weston MACHINE=stm32mp1 source layers/meta-st/scripts/envsetup.sh
```

`local.conf`에는 캐시 위치, 병렬 수, `rm_work`를 넣었다. 병렬 수는 `nproc`이 32라도 RAM에 맞춰 정해야 한다. C++ 컴파일 하나가 1~2GB를 쓰기도 하기 때문이다.

## 4. 첫 번째 관문 — ST 최소 이미지

```bash
bitbake st-image-core
```

첫 번째 걸림돌은 `envsetup.sh`였다. 실행하자 **설치되지 않은 호스트 패키지 목록**이 나왔다. 가이드에 넣어 둔 목록은 Yocto 공통 목록이었는데, ST는 그 외에 추가 패키지를 따로 검사한다. 표시된 대로 설치하고 다시 실행하니 넘어갔다.

그다음은 순조로웠고 **그래픽 없는 최소 이미지가 빌드됐다.** 이것으로 Scarthgap 빌드 환경이 정상임을 확인했다. 물론 이 이미지는 ST 공식 보드(DK2)용이라 SC6_0에서는 부팅되지 않는다. DDR 설정과 전원 구성(이 모듈에는 PMIC가 없다)이 다르기 때문이다.

## 5. 두 번째 관문 — EVerest를 Cortex-A7용으로

EVerest 저장소의 `yocto/` 폴더를 미리 읽어 두었다. 알아 둘 점이 두 가지 있었다.

- **레시피가 소스를 인터넷에서 받지 않는다.** 레이어가 들어 있는 **같은 clone 폴더의 소스**를 그대로 빌드한다. 그래서 `git checkout`한 버전이 곧 이미지에 들어가는 버전이다.
- **`meta-everest`만 추가하면 `meta-everest-common`은 자동으로 따라 들어온다.**

```bash
cd ~/stm32mp && git clone https://github.com/EVerest/EVerest.git
cd build-openstlinuxweston-stm32mp1
bitbake-layers add-layer ~/stm32mp/EVerest/yocto/scarthgap/meta-everest
bitbake everest-core
```

### 걸림돌 1: 다운로드 실패

```text
ERROR: ftxui-6.1.9-r0 do_fetch: Fetcher failure: ... git clone --bare --mirror
       https://github.com/ArthurSonzogni/FTXUI.git ... failed with exit code 128
```

EVerest가 쓰는 라이브러리 `ftxui`를 GitHub에서 받다 끊겼다. 빌드가 아니라 **다운로드** 단계의 문제다. 반쯤 받다 남은 파일을 지우고 다시 받았다. 이럴 때는 필요한 소스를 먼저 전부 받아 두는 게 낫다.

```bash
bitbake everest-core --runall=fetch
```

### 걸림돌 2: 버전이 내려갔다는 QA 에러

```text
ERROR: python3-packaging-21.3-r0 do_packagedata: QA Issue: Package version for package
       python3-packaging went backwards ... (from 0:23.2-r0.0 to 0:21.3-r0.0) [version-going-backwards]
```

이건 빌드 실패가 아니라 Yocto의 품질 검사가 막은 것이었다.

1. 4절의 ST 이미지를 빌드할 때 `python3-packaging`이 ST 기본 버전 **23.2**로 먼저 빌드됐다.
2. EVerest 레이어의 `recipes-backports/`에는 일부러 옛 버전 **21.3**이 들어 있다. 같은 폴더에 pydantic 1.10, marshmallow 3.20 등 EVerest가 맞춰 쓰는 Python 라이브러리들이 함께 있다.
3. 같은 빌드 폴더에서 버전이 내려가자, Yocto가 "패키지 배포 저장소가 깨질 수 있다"며 멈췄다.

이 검사는 업데이트 서버로 패키지를 배포할 때 의미가 있다. 시험 빌드에서는 경고로 낮춰도 된다.

```bash
# conf/local.conf
ERROR_QA:remove = "version-going-backwards"
WARN_QA:append = " version-going-backwards"
```

처음부터 EVerest 레이어를 넣고 새 빌드 폴더로 시작했다면 생기지 않았을 문제다. 제품 이미지에서는 충전기에 Python이 꼭 필요한지부터 따져 볼 생각이다. WSL 시뮬레이션에서 Python을 쓴 건 주로 가상 차량(PyEvJosev)이었다.

### 결과

**`bitbake everest-core` 성공.** EVerest가 32비트 Cortex-A7(`cortexa7t2hf-neon-vfpv4`)용으로 크로스 빌드됐다.

## 6. 위험 목록이 줄었다

| 위험 | 지난주 | 오늘 |
|---|---|---|
| OS 버전 (Dunfell) | EVerest 불가 | **Scarthgap 빌드 환경 확보** ✔ |
| **32비트 ARM 빌드** | 미확인 (빌드 PC 사양을 잘못 읽고 겁먹었던 부분) | **빌드 성공** ✔ |
| 메모리 | 여유 330MB vs 약 120MB | 충분할 것으로 봄 ✔ |
| **CPU 성능** (650MHz) | 미확인 | **여전히 미확인** — 빌드가 아니라 실행해 봐야 안다 |
| 우리 보드 이식 | 미착수 | 미착수 (DDR, PMIC 없는 전원, DTS) |

## 7. 만들어 둔 것: SD 카드에 올리는 법

다음 단계(우리 보드용 이식)를 위해 SD 카드 기록 절차도 가이드에 정리해 뒀다. 핵심은 세 가지다.

1. **지금 SD 카드는 보관하고 새 카드를 쓴다.** 먼저 `dd`로 통째로 백업해 둔다.
2. 빌드 결과의 `flashlayout_*/...sdcard*.tsv`를 ST 스크립트(`create_sdcard_from_flashlayout.sh`)로 `.raw` 하나로 만들고, `dd`나 `bmaptool`로 기록한다.
3. 부팅할 때는 시리얼 콘솔에서 **어디까지 가는지**를 본다. TF-A 단계에서 멈추면 DDR 설정 문제일 가능성이 크다.

```text
NOTICE:  BL2: v2.x ...     ← 여기서 멈추면 DDR
U-Boot 2023.xx ...
Starting kernel ...
... login:
```

`dd`의 `of=`에는 파티션(`/dev/sdb1`)이 아니라 장치 전체(`/dev/sdb`)를 쓰고, 시스템 디스크와 헷갈리지 않게 `lsblk`로 몇 번이고 확인한다.

## 정리

```text
지금까지                → OS를 빌드한 적 없음. MYiR 이미지 + 부품 교체
지금 SD 카드             → 9월의 .raw (eglfs, 1,536MB). Ubuntu 패키지는 7월 시도
Ubuntu였다면?            → 더 나쁨 (2018년, libsystemd 237)
ST Scarthgap 최소 이미지 → 빌드 성공 (호스트 패키지 추가 후)
EVerest                 → Cortex-A7용 빌드 성공
   ├ ftxui 다운로드 실패  → 다시 받기 / --runall=fetch
   └ packaging 버전 역행  → EVerest backports, QA를 경고로
남은 것                  → CPU 실측, 우리 보드 이식
```

두 질문 중 하나가 풀렸다. 지난주 "RAM 4GB, ARM64"라는 문구에 겁먹었던 게 무색하게, EVerest는 32비트 ARM용으로 아무렇지 않게 빌드됐다. 이제 남은 건 이 빌드 결과를 **진짜 SC6_0 위에서 돌려 보는 것**이다. 그러려면 이 OS가 먼저 우리 보드에서 부팅돼야 한다. 다음 관문은 DDR 설정과, PMIC 없는 이 모듈의 전원을 새 버전 위에 옮겨 심는 일이다.
