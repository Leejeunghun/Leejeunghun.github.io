오전과 오후에 걸쳐 손으로 하던 설치와 시스템 설정을 레이어로 옮겼다. 마지막 단계는 이것들을 **이미지 하나로 묶고, 빈 카드에 구워서 처음부터 다시 시험하는 것**이다. 지금까지 보드는 이것저것 손으로 넣은 파일이 쌓인 상태였다. 그래서 레이어만으로 같은 결과가 나오는지 확인할 방법은 새 카드뿐이다.

결과부터 정리하면 이렇다.

| 항목 | 결과 |
|---|---|
| 충전기용 이미지 레시피 `sc6-image` | 1,161개 패키지, 전체 빌드 24분 |
| 새 카드 회귀 시험 (M5 항목 전부 + WiFi/BT) | ✅ 전 항목 통과 |
| 시험 중 찾은 문제 | wait-online 실패(수정), BT 자동 켜기(원인 확인, 보류), 첫 부팅 유선 이더넷(조건 확인, 보류) |
| U-Boot 부팅 경고 3개 | 1개 수정, 1개 이미 사라짐, 1개 그대로 둠 |
| 브링업 흔적 정리 | 일회용 스크립트 79개 보관 폴더로 |

## 1. 충전기용 이미지 레시피

### 1-1. 그동안은 무엇으로 빌드했나

지금까지는 ST의 `st-image-core`를 빌드하고, 필요한 패키지는 빌드 PC의 `local.conf`에 넣었다.

```bitbake
# 빌드 PC conf/local.conf (지금까지)
IMAGE_INSTALL:append = " everest-core mosquitto bash procps"
```

`local.conf`는 그 빌드 PC에만 있는 파일이다. 다른 PC에서 레이어만 받아 빌드하면 EVerest가 빠진 이미지가 나온다. 그래서 이미지 구성을 레이어 안의 레시피로 옮겼다.

### 1-2. `sc6-image.bb`

```bitbake
# recipes-core/images/sc6-image.bb
SUMMARY = "KNV SC6_0 EV 완속충전기 이미지"

require recipes-st/images/st-image-core.bb

# 부팅마다 호스트 이름에 MAC 을 덧붙이는 ST 서비스 (2일차 참고)
CORE_IMAGE_EXTRA_INSTALL:remove = "st-hostname"

IMAGE_INSTALL += " everest-core mosquitto bash procps "
```

처음부터 새로 짜지 않고 `st-image-core`를 `require`했다. ST가 그 이미지에 넣어 둔 부팅·파티션 구성(초기 RAM 디스크, 파티션 레이아웃, 첫 부팅 때 rootfs 늘리기)을 그대로 쓰기 위해서다. 우리가 바꾼 것은 세 줄뿐이다. `local.conf`의 원래 줄은 주석으로 바꿨다.

### 1-3. 쓰지 않는 머신 기능 빼기

ST 머신 설정에는 평가보드 기준 기능이 켜져 있다. 충전기에는 화면도 오디오도 없다.

```bitbake
# conf/machine/stm32mp15-sc6.conf
MACHINE_FEATURES:remove = "splashscreen"
MACHINE_FEATURES:remove = "screen alsa pci tpm2"
```

빌드 후 이미지 패키지 목록(manifest)으로 확인했다. `alsa-utils` 하나는 남았다. ST의 `packagegroup-framework-tools-base-audio`가 직접 끌어오는 것이라 머신 기능과 상관이 없었다. 크기가 작고 해가 없어 그대로 두었다.

목록을 확인하다 한 번 헷갈린 것이 있다. `kernel-module-rfcomm`을 찾았는데 안 나왔다. 커널 모듈 패키지는 이름 뒤에 커널 버전이 붙는다.

```text
kernel-module-rfcomm-6.6.129   stm32mp15-sc6   6.6.129-stm32mp-r3.1-r0.13
```

### 1-4. 브링업용 TF-A 설정 지우기

M1(10/30)에서 TF-A가 콘솔 출력 전에 멈추는 문제를 쫓느라 넣은 bbappend가 있었다.

```bitbake
EXTRA_OEMAKE:append:stm32mp15-sc6 = " STM32MP_EARLY_CONSOLE=1 LOG_LEVEL=40"
```

이제는 필요 없어서 지웠다. 이때 주의할 점이 하나 있다. 우리 동기화 스크립트는 `tar`로 덮어쓰기만 하고 지우지는 않는다. WSL에서 `git rm`을 해도 빌드 PC에는 파일이 남는다. 빌드 PC 쪽 파일도 직접 지워야 했다.

### 1-5. SD 이미지 만들기에서 걸린 것

ST의 `create_sdcard_from_flashlayout.sh`는 같은 이름의 raw 파일이 있으면 묻는다.

```text
[WARNING]: A previous raw image already exists
    Do you want to overwrite the existing raw image? [Y/n]
```

ssh로 비대화형 실행을 하니 답을 못 받고 **예전 raw를 그대로 둔 채** 끝났다. 오류 없이 끝났지만 파일 시각을 보니 10/30 것이었다. 예전 raw를 먼저 지우고 `< /dev/null`로 실행하도록 바꿨다.

## 2. 새 카드 회귀 시험

카드 전체를 새 이미지로 덮어쓰고 처음부터 시험했다. 순서는 시스템 → 주변장치 → 무선 순이다.

| 단계 | 항목 | 결과 |
|---|---|---|
| 1. 시스템 | 호스트 이름 `sc6`, 시간대 KST | ✅ |
| | `/usr/local`(userfs 파티션)이 비어 있음 = 손으로 넣은 것 없음 | ✅ |
| | 우리 서비스 5개 active | ✅ |
| | PLC 펌웨어 자동 적재, 모뎀 MAC `02:4B:4E:56:00:03` | ✅ |
| | BT 확인 서비스 "정상" | ✅ |
| | `systemd-networkd-wait-online` | ❌ → 수정 후 ✅ (2-1) |
| 2. 주변장치 | 유선 이더넷 DHCP, ping | ✅ |
| | I2C6 ATECC608B 깨우기 응답 `04 11 33 43` | ✅ |
| | 전력량계 Modbus `01 03 02 01 63 f9 fd` | ✅ |
| | CP ADC 100% / 0% = 47936 / 1026 | ✅ |
| | DOUT1~4 LED, 릴레이 K1/K2 | ✅ |
| 3. 기타 | 외부 워치독 킥, USB OTG 디바이스/호스트, UART J8/J9 | ✅ |
| 4. 무선 | WiFi: 접속 정보 한 줄 추가 → 연결 → **재부팅 후 자동 연결** | ✅ |
| | BT: 페어링, SPP 양방향 | ✅ (2-2의 문제 있음) |

USB OTG 호스트 시험에서 한 번 "인식 안 됨"이 나왔다. 꽂은 것이 일반 USB 메모리였다. 이 포트는 USB-C 연결 방향으로 호스트/디바이스를 정하므로 OTG 어댑터가 필요하다. 지난번에도 비슷하게 헷갈렸던 부분이다.

### 2-1. wait-online 실패: 케이블 없는 USB 가젯

새 카드 첫 부팅에서 `systemctl --failed`에 하나가 나왔다.

```text
systemd-networkd-wait-online.service  loaded failed failed
```

wait-online은 networkd가 관리하는 인터페이스 중 **필수(RequiredForOnline)** 인 것이 모두 연결될 때까지 기다린다. 2일차에 PLC(`eth0`)와 WiFi(`wlan0`)는 필수에서 뺐는데, **USB 가젯(`usb0`)** 이 남아 있었다. `usb0`은 PC와 USB 케이블로 연결했을 때만 링크가 생기니, 평소에는 2분을 기다리다 실패한다.

`usb0` 설정은 ST 패키지(`usbotg-gadget-config`)의 `53-usb-otg.network`다. 이 파일을 덮어쓰지 않고 **drop-in** 으로 한 줄만 더했다.

```ini
# /usr/lib/systemd/network/53-usb-otg.network.d/sc6.conf
[Link]
RequiredForOnline=no
```

`X.network.d/*.conf`에 둔 파일은 원본 설정에 덧붙여진다. ST 패키지가 나중에 바뀌어도 우리 설정이 지워지지 않는다. 다시 빌드한 이미지에서도 확인했다.

```text
$ networkctl status usb0
                Network File: /usr/lib/systemd/network/53-usb-otg.network
         Required For Online: no
```

### 2-2. 블루투스가 매번 꺼진 채로 올라온다

페어링하려고 `discoverable on`을 했더니 거절됐다.

```text
[bluetooth]# discoverable on
Failed to set discoverable on: org.bluez.Error.Failed
```

`show`를 보니 `Powered: no`였다. `power on` 뒤에는 검색 허용도, 페어링도, SPP도 모두 됐다. 문제는 **부팅할 때마다 꺼져 있다**는 것이다. 어제도 매번 `power on`부터 했었다.

처음에는 칩 초기화가 늦어서 bluetoothd의 자동 켜기가 실패했다고 추정했다. 하지만 부팅 로그가 깨끗했다. 칩은 10초에 펌웨어까지 올라왔고, 확인 서비스도 복구 없이 "정상"으로 끝났다. 추정이 틀렸다.

다음으로 bluez 5.72의 자동 켜기 코드(`plugins/policy.c`)를 봤다.

```c
static bool auto_enable = false;
...
	conf = btd_get_main_conf();
	if (!conf)
		goto done;          /* 설정 파일이 없으면 false 그대로 */

	auto_enable = g_key_file_get_boolean(conf, "Policy", "AutoEnable", &gerr);
	if (gerr) {
		g_clear_error(&gerr);
		auto_enable = true; /* 파일은 있는데 키가 없으면 true */
	}
```

| 상황 | 자동 켜기 |
|---|---|
| `/etc/bluetooth/main.conf` **없음** | **안 함** |
| 파일은 있는데 `AutoEnable` 줄 없음 | 함 |
| `AutoEnable=true` | 함 |

빌드된 bluez 패키지를 풀어 보니 `/etc/bluetooth/`에는 `input.conf`와 `network.conf`만 있고 **`main.conf`가 없었다.** "설정 파일이 아예 없으면 꺼 두고, 파일만 있으면 켠다"는 동작이 좀 의외다. 그래도 원인은 이것 하나로 설명된다.

대책은 bluez bbappend로 `[Policy] AutoEnable=true` 한 줄짜리 `main.conf`를 넣는 것이다. 개발 중에는 `power on` 한 번이면 되니 **보류**했다. 그리고 SPP를 쓸 때는 어차피 `bluetoothctl`로 검색 허용을 켜야 한다.

덧붙여, 블루투스 데몬을 확인하라고 드린 `ps | grep bluetoothd`가 아무것도 출력하지 않아 잠깐 혼란이 있었다. 이번 이미지에 넣은 procps의 `ps`는 옵션이 없으면 **현재 터미널의 프로세스만** 보여 준다. `ps -ef`를 써야 한다.

## 3. U-Boot 부팅 경고 세 개

M2/M3(10/30) 때부터 U-Boot에 경고 세 개가 남아 있었다. 새 카드 부팅 로그로 하나씩 판단했다.

| 경고 | 판단 | 조치 |
|---|---|---|
| `serial@40010000: pinctrl_select_state_full ... err=-19` | 무해 | **수정** |
| `no /fwu-mdata node ?` | 무해 (정보 메시지) | 그대로 |
| `ENV offset invalid` | ST 레이아웃 카드에서는 **이미 사라짐** | 없음 |

### 3-1. `err=-19`: 재배치 전 단계의 핀 설정

U-Boot는 처음에 TF-A가 적재한 위치(0xC0100000)에서 최소한으로 돌다가, 자기 자신을 DDR 위쪽으로 옮긴(재배치) 뒤 본격적으로 동작한다. 재배치 전 단계에서는 **`bootph-all` 표시가 붙은 DT 노드만** 장치로 만든다.

빌드된 U-Boot DTB를 풀어 보니 콘솔 UART4의 핀 노드(`uart4-0`)에 이 표시가 없었다. 그래서 UART 드라이버가 핀 설정을 찾다가 `-ENODEV`(-19)를 받은 것이다. 핀은 TF-A가 이미 잡아 두어서 콘솔은 정상으로 나왔다. 메시지만 남은 셈이다.

```dts
/* mx/sc6/CA7/DeviceTree/sc6/u-boot/stm32mp157a-sc6-u-boot.dtsi */
&uart4 {
	bootph-all;
};

&uart4_pins_a {
	bootph-all;
	pins1 {
		bootph-all;
	};
	pins2 {
		bootph-all;
		bias-pull-up;
	};
};
```

U-Boot DTS는 외부 DT라서 bitbake가 변경을 알아채지 못한다. 그래서 `u-boot-stm32mp`와 `fip-stm32mp`를 `cleansstate` 한 뒤 다시 빌드했다. FIP 시각과 DTB의 `bootph-all`로 반영을 확인했다. 새 카드로 부팅하니 OP-TEE 줄 바로 다음에 U-Boot 배너가 나오고, 그 사이에 있던 경고가 사라졌다.

### 3-2. `no /fwu-mdata node ?`

U-Boot의 A/B 펌웨어 업데이트(FWU) 기능이 메타데이터 저장 위치를 적은 DT 노드를 찾다가 못 찾았다는 정보 메시지다. ST도 이 노드를 DK2와 EV1 보드에만 넣었고, 우리 기준인 DK1에는 없다. 원격 업데이트나 eMMC 이전 방식을 정할 때 같이 보기로 했다.

### 3-3. 함께 보인 것: TF-A의 `INFO` 줄과 `(debug)`

조기 콘솔 bbappend를 지웠는데도 TF-A가 `INFO:` 줄을 잔뜩 찍고 버전에 `(debug)`가 붙어 있었다. 빌드 PC에서도 파일이 지워진 것을 확인했고, TF-A도 다시 빌드됐다. 원인은 ST 배포판이 **개발용으로 디버그 출력을 켜 둔 기본값**이었다.

```bitbake
# meta-st-stm32mp/conf/machine/include/st-machine-common-stm32mp.inc
ST_TF_A_DEBUG_TRACE ?= "${@bb.utils.contains('ST_DEBUG_TRACE', '1', '1', '0', d)}"
```

OP-TEE의 `This OP-TEE configuration might be insecure!` 경고도 같은 맥락이다. 제품 빌드에서 `ST_DEBUG_TRACE = "0"`으로 끄는 항목으로 적어 두었다.

## 4. 브링업 흔적 정리

| 대상 | 한 일 |
|---|---|
| WSL 빌드·분석 스크립트 110개 | 계속 쓰는 31개만 남기고 79개를 `archive/`로 이동 (삭제 아님) |
| 빌드 PC `~/sc6-out` | 레이어 이전에 손으로 배포하던 파일(`rfcomm.ko`, 펌웨어 묶음 등)을 `old-manual/`로 |
| 빌드 PC `local.conf`의 `OLDEST_KERNEL = "5.4"` | **유지**, 주석만 갱신 |

`OLDEST_KERNEL`은 10/29에 MYiR 5.4 커널 위에서 새 rootfs를 chroot로 돌려 보려고 낮춘 값이다. 보드가 6.6이 된 지금은 필요 없다. 하지만 되돌리면 glibc부터 거의 전체(약 2,500개 작업)를 다시 빌드한다. 기능상 차이는 거의 없어서 제품 빌드를 정리할 때 판단하기로 했다.

남은 스크립트는 역할별로 이렇다.

```text
레이어   sync-layer.sh  commit-layer.sh
빌드     build-recipe.sh  build-sc6-image.sh  build-kernel-dtb.sh  build-tfa.sh
확인     check-*.sh  verify-*.sh
소스     pull-*-patched.sh  grep-*.sh  show-*.sh  extract-dtb.py
SD       sc6-tfa-sd.sh  push-sd-script.sh
```

## 5. 다시 빌드한 이미지와 유선 이더넷 문제

usb0 drop-in과 U-Boot 수정을 넣어 다시 빌드했다(이미지 6분). 새 카드에 구워 부팅하니 또 `degraded`였다.

```text
$ systemctl --failed --no-legend
* systemd-networkd-wait-online.service loaded failed failed
```

이번에는 랜 케이블이 빠져 있었다. WiFi 접속 정보도 새 카드라 비어 있었으니, 연결된 네트워크가 하나도 없어 실패한 것은 당연하다. 케이블을 꽂고 wait-online을 다시 돌렸는데 **또 2분을 기다리다 실패했다.**

### 5-1. end0이 꺼진 채로 남아 있다

```text
$ networkctl
  2 end0  ether    off         configuring
  5 usb0  gadget   no-carrier  configuring
```

usb0은 `Required For Online: no`로 제대로 적용돼 있었다. 문제는 end0의 `off`였다. 케이블이 없으면 `no-carrier`가 나와야 한다. `off`는 인터페이스 자체가 꺼져 있다는 뜻이다.

```text
end0: PHY [stmmac-0:06] driver [YT8511 Gigabit Ethernet] (irq=POLL)
stm32-dwmac 5800a000.ethernet: Failed to reset the dma
end0: stmmac_hw_setup: DMA engine initialization failed
end0: __stmmac_open: Hw setup failed
```

```text
systemd-networkd: end0: Could not bring up interface, ignoring: Connection timed out
```

STM32의 이더넷 MAC(stmmac)은 인터페이스를 켤 때 DMA를 초기화한다. 이 초기화가 끝나려면 **PHY가 보내 주는 RGMII 수신 클럭**이 들어와야 한다. 클럭이 없으면 시간 초과로 실패한다. networkd는 실패를 `ignoring`으로 넘기고 다시 시도하지 않는다. 그래서 나중에 케이블을 꽂아도 end0은 계속 꺼져 있었다.

의심 가는 곳은 PHY의 절전 모드였다. 6.6 드라이버(`drivers/net/phy/motorcomm.c`)를 보면 같은 회사의 YT8521은 확장 레지스터 0x27의 bit 15로 절전을 끄는 코드가 있다. 반면 우리 PHY인 **YT8511은 같은 레지스터에서 "절전 중 PLL 유지"(bit 14)만 켜고 절전 자체는 끄지 않는다.** 케이블이 없어서 PHY가 절전에 들어가 수신 클럭을 멈췄다면 로그와 맞는다.

### 5-2. 재현해 보니 조건이 좁아졌다

| 시험 | 결과 |
|---|---|
| 새 카드 첫 부팅, 케이블 없음 | ❌ 실패 |
| 케이블 꽂고 `ip link set end0 up` | ✅ |
| 케이블 뽑고 `down` → `up` | ✅ |
| 케이블 없이 `reboot` | ✅ (19초에 켜짐) |
| **케이블 없이 전원 껐다 켜기** | ✅ |

"케이블 없이 부팅하면 실패"라고 생각했는데, 일반 부팅으로는 재현되지 않았다. 차이는 **시각**이었다.

```text
첫 부팅:  [117.8] end0: Register MEM_TYPE_PAGE_POOL RxQ-0   ← 실패
재부팅:   [ 19.3] end0: Register MEM_TYPE_PAGE_POOL RxQ-0   ← 성공
```

새 카드의 첫 부팅에서는 ST 이미지가 rootfs를 카드 크기에 맞게 늘리느라 1분 넘게 걸린다. 그래서 networkd가 117초에야 end0을 켰다. PHY는 전원이 들어온 뒤 2분 가까이 링크 없이 있었던 것이다. 평소 부팅처럼 20초 안에 켜면 아직 절전에 들어가기 전이라 성공하는 것으로 보인다. 직접 끄고 켠 시험은 `down` 때 리눅스가 PHY를 전원 차단 상태로 바꾸고, `up` 때 새로 깨우니 역시 성공한다.

실패 조건은 "**PHY가 전원 투입 후 오래 링크 없이 있다가 처음 켜질 때**"로 좁혀졌다. 현장에서는 새 카드나 eMMC의 공장 첫 부팅 정도이고, 재부팅 한 번이면 풀린다. 정전 후 복구처럼 걱정했던 상황은 콜드 부팅 시험으로 문제없음을 확인했다. 그래서 우선순위를 낮췄다. 대책 후보는 두 가지로 적어 두었다.

- YT8511 초기화에서 레지스터 0x27 bit 15를 지워 절전을 끄는 커널 패치
- end0 켜기가 실패하면 다시 시도하는 서비스

이 문제는 "필수 인터페이스가 모두 연결돼야 한다"는 wait-online 덕분에 드러났다. 충전기는 설치 현장이나 통신 장애로 네트워크 없이 켜질 수 있다. 그때 2분 대기와 `degraded`를 어떻게 다룰지는 EVerest가 무엇을 기다리는지 보고 M7에서 정한다.

|---|---|---|

| 첫 부팅 end0 켜기 실패 | YT8511 절전 추정, 늦게 켤 때만 | 절전 끄는 패치 또는 재시도 |

### 오늘 배운 것

1. **새 카드 시험은 손으로 쌓인 것을 걷어 낸다.** 기존 보드에서는 손으로 넣은 `/etc` 파일 덕분에 보이지 않던 usb0 문제가 바로 드러났다.
2. **"스크립트가 끝났다"와 "결과가 나왔다"는 다르다.** SD raw 생성은 오류 없이 끝났지만 질문에 답을 못 받아 예전 파일을 그대로 두었다. 결과 파일의 시각을 보자.
3. **기본값은 코드에서 확인하자.** bluez의 자동 켜기는 "설정 파일이 없으면 꺼짐, 파일만 있으면 켜짐"이었다. 문서만 봐서는 짐작하기 어렵다.
4. **첫 추정이 틀리면 로그로 돌아가자.** 블루투스는 "칩 초기화 타이밍"으로, 이더넷은 "케이블 없으면 항상 실패"로 처음에 추정했지만 둘 다 로그와 재현 시험에서 틀렸다.
5. **재현이 안 되면 조건의 차이를 표로 놓자.** 실패한 부팅과 성공한 부팅을 나란히 놓으니 117초와 19초라는 차이가 보였다.
6. **실패를 `ignoring`으로 넘기는 곳을 조심하자.** networkd는 인터페이스 켜기 실패를 한 줄 남기고 넘어간다. 그 뒤로는 케이블을 꽂아도 아무 일도 일어나지 않는다.
